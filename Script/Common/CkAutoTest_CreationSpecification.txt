//============================================================================
// CK AUTOMATION TEST FRAMEWORK — CREATION SPECIFICATION
//============================================================================

/*
This spec describes the AUTOMATION TEST framework provided by CkTests. It is
project-agnostic: BusterBlock, future projects, and CkTests' own framework
tests all use the same harness.

For the gym framework (visual, manually-driven, no assertions), see:
  CkGym_CreationSpecification.txt

Gyms and AutoTests serve different purposes:
  - Gyms = visual playgrounds for eyeballing a feature.
  - AutoTests = headless assertions that pass/fail in Session Frontend / CI.

A single feature can have BOTH (the gym demonstrates the feature; the
AutoTest verifies it). They share the same .as files where convenient
(both call utils_*::Add, BindTo_*, etc.) but they're independent — the
AutoTest does not need the gym, and vice versa.
*/

//============================================================================
// !!! READ THIS FIRST — THE WORKFLOW IS NOW FULLY AUTOMATED !!!
//============================================================================
//
// Authoring an autotest is a ONE-PART workflow. Write the entity-script .as
// file. Save. Done. The editor pipeline takes care of the rest:
//
//   1. CkAutoTestWrapperGenerator (CkFoundation) — emits the matching
//      A<...>_Actor wrapper class into <Plugin>/Script/Generated/
//      <Plugin>_AutoTestActors.as on every AS post-compile.
//
//   2. UCkAutoTestMapPopulator (CkTestsEditor) — per-config sync that
//      spawns the wrapper actor into the right AutoTests level, sets a
//      readable Outliner label, and auto-saves the level. Triggered by
//      AS post-compile, AssetRegistry first-load, or the
//      `Ck.SyncAutoTestMaps` console command.
//
// IF YOU (HUMAN OR LLM) JUST CREATED OR MODIFIED A TEST:
//   1. Save the .as file. AS auto-recompiles; the wrapper appears in
//      Script/Generated/<Plugin>_AutoTestActors.as.
//   2. The populator runs (you'll see `[CkAutoTest Populator] === ...`
//      in Output Log) and places the wrapper actor into the configured
//      AutoTests level. The level does NOT need to be open — the populator
//      will load the .umap off-disk, edit it, and save it back transparently.
//   3. Hit the **refresh button in Session Frontend's Automation tab** to
//      re-scan for tests. The whole pipeline above is invisible to Session
//      Frontend's cached test list, so without a refresh new tests won't
//      show up — even though they're properly placed in the level on disk.
//   4. Check the test → Start Tests. (Or console: `Automation RunTests
//      <pattern>`.)
//
// IF YOU SEE A TEST IN THE .AS FILE BUT NOT IN SESSION FRONTEND:
//   - **Refresh Session Frontend first** (step 3 above — it caches its
//     discovered test list and won't see new placements until refreshed).
//   - Check Output Log for the populator's last summary line — did it find
//     the test? If so, the wrapper actor was spawned in the AutoTests map.
//   - Is there a UCkAutoTestMapConfig for the plugin/project authoring
//     the test? See section 9b for setup.
//   - Did AS report a compile error? A broken .as file blocks PostCompile
//     and stops the generator from running. Fix the AS error first.
//
// The full per-step authoring workflow is in section 5 (file template),
// 5b (per-project config asset), and 9 (one-time map setup).
//
// HISTORICAL NOTE: earlier versions of this framework required authors to
// hand-write the `A<...>_Actor` wrapper class next to the entity script and
// drag it into the AutoTests map manually from the Place Actors panel. Both
// steps are now automated. Hand-authored wrappers still work as an opt-out
// (the generator detects them by class name and skips emission for that
// test) — useful if you need a non-default `_TimeoutSeconds` or a fully
// custom subclass.

//============================================================================
// 1. ARCHITECTURE OVERVIEW
//============================================================================

// Three layers — runtime harness, editor automation, per-test code.
//
//   Layer A — Reusable runtime harness (lives in CkTests):
//     C++:
//       FCk_AutoTest_Result            — USTRUCT result fragment
//       ECk_AutoTest_Status            — Pending/Running/Passed/Failed/TimedOut
//       UCk_Utils_AutoTest_UE          — Set_Result / Has_Result / Get_Result
//       ACk_AutoTestRunner             — AFunctionalTest subclass that drives
//                                        the AS test, applies _TimeoutSeconds
//                                        to the engine TimeLimit, and reports
//                                        pass/fail
//     AngelScript:
//       UCk_AutoTest_Base              — base entity script: Assert_*,
//                                        FinishSuccess/Failure
//
//   Layer B — Editor automation (CkAngelscriptGenerator + CkTestsEditor):
//       FCkAutoTestWrapperGenerator    — on every AS post-compile, scans
//                                        live UCk_AutoTest_Base subclasses
//                                        and emits matching A<...>_Actor
//                                        wrapper classes into <Plugin>/Script/
//                                        Generated/<Plugin>_AutoTestActors.as.
//                                        The emitted wrapper resolves its
//                                        entity-script class at runtime via
//                                        FSoftClassPath rather than a compile-
//                                        time `default` reference — so the
//                                        generated file always compiles, even
//                                        if an entity-script .as gets deleted
//                                        out from under it. Self-healing on
//                                        the next pass; no race conditions.
//                                        See the generated file's header for
//                                        the full rationale.
//                                        Skips emission for any test whose
//                                        wrapper class already exists with a
//                                        non-Generated/ source path (the
//                                        opt-out mechanism for hand-authored
//                                        wrappers).
//       UCkAutoTestMapConfig           — UDataAsset (typically authored as
//                                        an AS `asset` declaration) carrying
//                                        target map + auto-save toggle +
//                                        optional scope override.
//       UCkAutoTestMapPopulator        — UEditorSubsystem that, per config,
//                                        ensures one placed wrapper actor
//                                        per discovered test class in the
//                                        config's target level. Triggers on
//                                        AssetRegistry first-load, AS post-
//                                        compile, or `Ck.SyncAutoTestMaps`.
//
//   Layer C — Per-test code (lives in the project):
//     One AS file per test, declaring ONE class — the entity script
//     (subclass of UCk_AutoTest_Base). The corresponding actor wrapper
//     is auto-generated and auto-placed by Layer B. Authors only need
//     to hand-write a wrapper for advanced cases (custom _TimeoutSeconds,
//     fully custom subclass). See section 5b for opt-out details.
//
// Lifecycle (single test run):
//
//   PIE starts on the test map
//       -> AFunctionalTest framework picks up the placed *_Actor
//       -> Runner.PrepareTest syncs TimeLimit to _TimeoutSeconds, then
//          spawns the AS entity on the transient entity via Request_SpawnEntity
//       -> AS DoConstruct runs (base writes Status=Running result fragment)
//       -> AS DoBeginPlay runs (subclass: exercise feature, bind signals)
//       -> Test eventually calls FinishSuccess / FinishFailure
//          -> base class writes Status=Passed/Failed result fragment
//       -> Runner.Tick polls Has_Result; on terminal status, calls
//          FinishTest(Succeeded/Failed, message)
//       -> Session Frontend shows green/red row + assertion message
//
//   If the AS test never writes a terminal result, the engine TimeLimit
//   fires automatically (TimesUpResult=Failed) — no extra harness logic.

//============================================================================
// 2. WHEN TO USE THIS HARNESS (vs C++ FAutomationTestBase)
//============================================================================

// USE THIS HARNESS when the feature under test:
//   - Has processors that mutate state (CkAttribute, CkTimer, Economy, etc.)
//   - Uses Request_*, BindTo_*, signal/messaging infrastructure
//   - Spawns entities, attaches fragments, listens for delegates
//   - Anything that requires a ticking world to behave correctly
//
// In practice, this is ~95% of CkFoundation features and ~all of project
// gameplay code. Decision rule:
//
//   Does the test need processors to tick / signals to fire / a world to exist?
//   |--- Yes -> AS test via this harness.
//   |--- No  -> Plain C++ FAutomationTestBase (no harness needed).
//
// USE PURE C++ TESTS (FAutomationTestBase / IMPLEMENT_SIMPLE_AUTOMATION_TEST)
// only for genuinely-non-world utilities:
//   - ck::Format string utilities
//   - ck::algo::* algorithm helpers
//   - FCk_Chrono / FCk_ValueRange math
//   - SPUD save shape / serialization round-trips
//   - Compile-time / template constraint checks
//   - Any code path that does NOT touch FCk_Handle, processors, or signals
//
// See section 14 for the C++ unit-test layout, naming, and reference example.
//
// NEVER write tests in Blueprint. BPs work via the same UFUNCTION dispatch
// AS uses, but BPs are binary assets — terrible for diffs, code review,
// version control. AS-authored tests are the standard.

//============================================================================
// 3. DEPENDENCY DIRECTION (where tests live)
//============================================================================

// CkFoundation <- CkTests <- ProjectModule (e.g. BusterBlock)
//
// Tests follow the same direction:
//
//   CkFoundation feature tests (CkAttribute, CkTimer, etc.):
//     -> Plugins/CkTests/Script/<ModuleName>/CkAutoTest_<Module>_<Scenario>.as
//
//   Project-specific feature tests (Economy, Inventory, etc. for BusterBlock):
//     -> ProjectRepo/Script/Tests/<Feature>/<Prefix>_AutoTest_<Feature>_<Scenario>.as
//
// The harness in CkTests must NOT depend on project-specific types. The
// per-test AS files own all feature-specific knowledge. The C++ harness only
// references the AS class via TSubclassOf<UCk_EntityScript_UE> and the
// generic FCk_AutoTest_Result struct.

//============================================================================
// 4. NAMING CONVENTIONS
//============================================================================

// Entity-script class:    U<Prefix>_AutoTest_<Feature>_<Scenario>
//   Examples:
//     UCk_AutoTest_Attribute_IntegerBasic        (CkTests, Ck prefix)
//     UBb_AutoTest_Economy_BasicFlow             (BusterBlock, Bb prefix)
//   Authored in the per-test .as file.
//
// Actor wrapper class:    A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor
//   Examples:
//     ACk_AutoTest_Attribute_IntegerBasic_Actor
//     ABb_AutoTest_Economy_BasicFlow_Actor
//   Auto-generated by FCkAutoTestWrapperGenerator into
//     <Plugin>/Script/Generated/<Plugin>_AutoTestActors.as
//   The naming convention IS load-bearing — the generator computes the
//   wrapper name as `A` + entity-script-name-with-`U`-stripped + `_Actor`,
//   and the populator strips the `_Actor` suffix to derive the Outliner
//   label shown in Session Frontend. Don't deviate.
//
// File name:              <Prefix>_AutoTest_<Feature>_<Scenario>.as
//   Holds the entity-script class (and only that, in the typical case).
//
// Folder layout:
//   CkTests:    Plugins/CkTests/Script/<Module>/CkAutoTest_*.as
//   Project:    Script/Tests/<Feature>/<Prefix>_AutoTest_*.as
//
// Test scenario name (the <Scenario> portion):
//   Should describe what the test verifies, not what it does. Good:
//     BasicFlow, MoneyFloor, XPOverflow, IntegerBasic, ClampMaxValue.
//   Bad:
//     Test1, Sanity, Demo, ScratchPad.

//============================================================================
// 5. FILE TEMPLATE
//============================================================================

// Every test file follows this shape — ONE class. The actor wrapper is
// auto-generated by Layer B (see section 1) into Script/Generated/
// <Plugin>_AutoTestActors.as on the next AS recompile. Don't write it
// by hand unless you need an opt-out (section 5b).

// DEFAULT SHAPE — a linear test, declared as named steps. Do NOT hand-roll a
// `_Step` counter with `if (_Step == N)` dispatch in signal handlers: that was
// the pre-sequencer shape, and it hides WHY a test is waiting when it hangs.

class U<Prefix>_AutoTest_<Feature>_<Scenario> : UCk_AutoTest_Base
{
    // ---- Per-test state (handles + observation fields only; no step counter) ----

    private FCk_Handle_<Feature> _Feature;

    // ---- Lifecycle: subclasses override DoBeginPlay only ----
    //
    // The base class (UCk_AutoTest_Base) handles DoConstruct: it adds the
    // timeout timer and initializes the Result fragment to Status=Running.
    // Do NOT override DoConstruct unless you have a specific reason to.

    UFUNCTION(BlueprintOverride)
    void DoBeginPlay(FCk_Handle InHandle)
    {
        // 1. Set up the feature being tested.
        //    NOTE: most utils_*::Add calls take FCk_Handle& (ref). DoBeginPlay
        //    receives FCk_Handle by value; copy to a local lvalue first.
        auto LocalHandle = InHandle;
        auto Params = FCk_Fragment_<Feature>_ParamsData(...);
        _Feature = utils_<feature>::Add(LocalHandle, Params, ECk_Replication::DoesNotReplicate);

        // 2. Declare the sequence. Descriptions are what a hang reports, so
        //    write each as the thing that must become true.
        Add_Step("request the mutation", n"Step_Request");
        Add_Step_WaitUntil("the new value is visible", n"Check_ValueApplied");
        Add_Step("assert the outcome", n"Step_Assert");

        // 3. Run it. The last step finishing PASSES the test — no trailing
        //    FinishSuccess(), and no IsFinished() guard inside step bodies.
        Run_Steps(LocalHandle);
    }

    // ---- Action step: FCk_Lambda_InHandle ----

    UFUNCTION()
    private void Step_Request(FCk_Handle InHandle, FInstancedStruct InPayload)
    {
        utils_<feature>::Request_DoSomething(_Feature, ...);
    }

    // ---- Predicate: FCk_Predicate_InHandle_OutResult ----
    //
    // Answer through a LOCAL COPY — AngelScript rejects a non-const call on a
    // by-value struct param. FCk_SharedBool is a shared cell, so the copy
    // writes the same bool.
    //
    // Before writing a predicate, run the five rules in CkTests/CLAUDE.md
    // ("Choosing a wait"). The one that catches most mistakes: if the system
    // did nothing at all, would this still be true? If yes it is a NEGATIVE
    // and must NOT become a predicate — keep a settle, and make it meaningful
    // with a positive assertion before it.

    UFUNCTION()
    private void Check_ValueApplied(FCk_Handle InHandle, FCk_SharedBool OutResult, FInstancedStruct InPayload)
    {
        auto Res = OutResult;
        Res.Set(utils_<feature>::Get_Value(_Feature) == <expected>);
    }

    UFUNCTION()
    private void Step_Assert(FCk_Handle InHandle, FInstancedStruct InPayload)
    {
        Assert_Equals_Int(utils_<feature>::Get_Value(_Feature), <expected>,
            "What this assertion verifies");
    }
}

// BRANCHING SHAPE — for signal-driven or authority-split flows that are not a
// straight line, use the standalone waits instead of a step list. The
// continuation takes the FCk_Delegate_Timer signature and may start the next
// wait, so each hop reads as "what must hold before the next thing happens".
//
//     UFUNCTION()
//     private void OnSomeSignal(FCk_Handle_<Feature> InHandle, <Payload> InPayload)
//     {
//         if (IsFinished()) { return; }
//         WaitUntil(n"Check_Settled", n"OnSettled");   // budget 0 = until test timeout
//     }
//
//     UFUNCTION()
//     private void OnSettled(FCk_Handle_Timer InTimer, FCk_Chrono InChrono, FCk_Time InDeltaT)
//     {
//         if (IsFinished()) { return; }
//         Assert_True(..., "...");
//         FinishSuccess();
//     }
//
// WaitFrames(N, n"Continue") is the frame-counted twin — use it ONLY when there
// is no observable condition (i.e. when asserting something does NOT happen),
// and only when you can say what N counts. WaitOneFrame is LEGACY: it is a
// 0.05s timer (~3 passes at 60fps), NOT a frame wait. It is retained so
// unmigrated tests compile, and it remains the correct call where a window was
// tuned against that duration — swapping in a small WaitFrames(N) SHORTENS it.

// That's it. After saving the .as file, the generator emits this:
//
//   // Script/Generated/<Plugin>_AutoTestActors.as  -- DO NOT EDIT
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       UFUNCTION(BlueprintOverride)
//       TSubclassOf<UCk_EntityScript_UE> Get_TestEntityScriptClass() const
//       {
//           auto Path = FSoftClassPath(
//               "/Script/Angelscript.Ck_AutoTest_<Feature>_<Scenario>");
//           TSubclassOf<UCk_EntityScript_UE> ResolvedClass;
//           ResolvedClass = Path.TryLoadClass();
//           return ResolvedClass;
//       }
//   }
//
// (The runtime FSoftClassPath form — instead of the simpler-looking
//  `default _TestEntityScriptClass = U...;` — exists to make the generated
//  file race-immune against filesystem .as deletes. See the generated file's
//  header comment for the full why. You don't need to know this to author
//  tests; the generator handles the form for you.)
//
// The populator places one instance of that wrapper into the configured
// AutoTests level. Hit refresh in Session Frontend's Automation tab and
// the new test row appears.

//----------------------------------------------------------------------------
// 5a. ESCAPE HATCH: dynamic test-class resolution
//----------------------------------------------------------------------------
//
// If a wrapper needs to compute its test class at runtime (e.g. based on a
// console var), hand-author the wrapper and override Get_TestEntityScriptClass:
//
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       UFUNCTION(BlueprintOverride)
//       TSubclassOf<UCk_EntityScript_UE> Get_TestEntityScriptClass() const
//       { return SomeCondition ? UClassA : UClassB; }
//   }
//
// The generator detects the hand-authored wrapper by class name and skips
// emission for that test, so the runtime override is authoritative.

//----------------------------------------------------------------------------
// 5b. PER-TEST TIMEOUT (and the rare-case opt-out)
//----------------------------------------------------------------------------
//
// CUSTOM TIMEOUT (the common case):
//   Override _TimeoutSeconds directly on the entity-script class. The
//   generator reads the CDO, sees the override, and propagates it to
//   the wrapper's _TimeoutSeconds field — which the C++ runner reads
//   in PrepareTest to set AFunctionalTest::TimeLimit.
//
//   class U<Prefix>_AutoTest_<Feature>_<Scenario> : UCk_AutoTest_Base
//   {
//       default _TimeoutSeconds = 2.0f;   // fail-fast race test
//       // ... test body ...
//   }
//
//   Reference: CkAutoTest_StateMachine_RacingEventDrivenTransitions.as.
//   No wrapper file to write — the generator handles everything.
//
// WRAPPER-LEVEL OPT-OUT (rare):
//   For tests that need wrapper customization beyond timeout (e.g. a fully
//   custom Get_TestEntityScriptClass override that picks the test class
//   based on a console var), hand-author the wrapper next to the entity-
//   script class:
//
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       default _TestEntityScriptClass = U<Prefix>_AutoTest_<Feature>_<Scenario>;
//       UFUNCTION(BlueprintOverride)
//       TSubclassOf<UCk_EntityScript_UE> Get_TestEntityScriptClass() const
//       { return SomeCondition ? UClassA : UClassB; }
//   }
//
//   The generator detects any class with the conventional `A<...>_Actor`
//   name living OUTSIDE Script/Generated/ as hand-authored and skips
//   emission for that test.
//
//   Note: hand-authored wrappers can use the simpler compile-time
//   `default _TestEntityScriptClass = U...;` form because both classes
//   live in the same .as file — deleting the file removes both atomically,
//   no stale generated wrapper to leave the editor in a bad state.

//============================================================================
// 6. THE BASE CLASS API (UCk_AutoTest_Base)
//============================================================================

// Construction (handled by base, do not override unless you need to):
//   - DoConstruct: adds a TAG_CkAutoTest_Runner tag, initializes the
//     Result fragment to Status=Running.
//
// Timeout: set `default _TimeoutSeconds` on the ENTITY SCRIPT; the wrapper
// generator propagates it to the generated wrapper CDO. (The older wording
// below, describing the wrapper as the place to configure it, is stale.)
//   class A..._Actor : ACk_AutoTestRunner
//   {
//       default _TimeoutSeconds = 3.0f;   // optional; default is 5s
//   }
// The C++ runner syncs the engine's TimeLimit to _TimeoutSeconds in
// PrepareTest, so there is exactly one knob to configure per test.

// Assertion helpers (call from signal handlers or step functions):
//
//   void Assert_True(bool Condition, const FString& Message);
//   void Assert_Equals_Int(int32 Actual, int32 Expected, const FString& Message);
//   void Assert_Equals_String(const FString& Actual, const FString& Expected,
//                             const FString& Message);
//
// Each assertion increments AssertionsRun. On failure, it increments
// AssertionsFailed and stashes the message as the first failure reason.
// Assertions do NOT auto-finish the test — the subclass decides when.

// Finish helpers (call exactly one of these to end the test):
//
//   void FinishSuccess();                          // No-op if already finished
//   void FinishFailure(const FString& Message);    // No-op if already finished
//   bool IsFinished() const;                       // Use as guard at the
//                                                  // top of signal handlers

// Timeout (automatic):
//   If FinishSuccess/Failure is never called within _TimeoutSeconds (set
//   on the actor wrapper, default 5s), the engine's AFunctionalTest
//   TimeLimit fires and the test is reported as failed. There is no
//   AS-side timer — the engine handles this directly.

// Cleanup — MANDATORY if you spawn anything outside the runner's subtree:
//
//   protected void Track_ForCleanup(FCk_Handle InOwner);
//
// ALL AUTOTESTS SHARE ONE PIE WORLD. The harness's per-test teardown
// (ACk_AutoTestRunner::Destroy_RunnerEntity) cascades ONLY the runner's own
// lifetime subtree. Anything you parent elsewhere survives your test and lives
// on into every test that runs after it:
//
//   - anything spawned UNDER an ActorRelay channel entity (the mandated anchor
//     for any entity script that replicates), and the subordinates a driver
//     spawns and exposes (e.g. Get_EmployeeManager()) — a driver may anchor its
//     OWN subordinates to the channel, in which case destroying the driver does
//     NOT cascade them;
//   - anything created under ck::TransientEntity();
//   - actors you spawned (destroy the actor, or the entity that owns it).
//
// This is not a local problem. Features discover their subjects by WORLD-scoped
// tag-scan (a world item-cap driver scans every source; an NPC's store link sets
// CanShop=true on ANY ready store driver), so ONE leaked entity silently breaks
// UNRELATED tests, far away from the test that leaked it, in ways that look like
// flakes. Register every out-of-subtree ROOT:
//
//   Track_ForCleanup(FCk_Handle(SpawnedDriver));   // typed handles: wrap
//   Track_ForCleanup(TransientOwnedEntity);
//
// Register it as soon as the handle is valid, and BEFORE any early-return
// (a failed cast that FinishFailure()s must still clean up). The base
// deferred-destroys them at finish, sequenced destroy -> settle -> result-write
// so cleanup can never race the result the C++ runner polls. Invalid handles are
// ignored, so tracking something you also destroy yourself is a harmless no-op.
//
// *** NEVER Track_ForCleanup the ActorRelay CHANNEL entity itself. ***
// Channels are POOLED and SHARED with live production subsystems; the API is
// acquire-only by design (acquisition is stateless pool selection — there is no
// checkout to return), and for Generic groups the pool NEVER regrows. Destroying
// one kills ActorRelay for the rest of the PIE session — every test after yours.
// Track what you spawned UNDER the channel, never the channel.
//
// Timeouts no longer bypass this. The engine's TimeLimit reports a timeout WITHOUT running the
// AS finish path, which used to mean a timed-out test leaked everything it had tracked. The base
// now arms its own deadline at 0.9x _TimeoutSeconds — lazily, on your FIRST Track_ForCleanup, so
// a test that tracks nothing pays no timer — and fails through Finalize instead, which cleans up
// and reports how many owners were still outstanding. A test that trips it is still a bug: fix
// the timeout. It just no longer takes the rest of the lane down with it.

// Environment restoration — the OTHER half of isolation:
//
//   protected void Set_CVarForTest(FName InName, const FString& InValue);
//   protected void Snapshot_CVarForTest(FName InName);
//
// Track_ForCleanup covers ECS entities. It does NOT cover process-global state,
// and NOTHING else in the harness does either. A lane is one editor process and
// one map load, so every console variable, subsystem flag, registry entry and
// on-disk config a test moves is still moved when the next test starts.
//
// This produces the single most expensive failure shape in this corpus: a test
// that is green on its own and red in the suite. The red lands on an innocent
// downstream test, so the signal points at the victim and never at the culprit,
// and the "fix" that makes the victim green again is usually a tolerance bump
// that hides the leak instead of removing it.
//
// CONSOLE VARIABLES — use Set_CVarForTest, never ExecuteConsoleCommand:
//
//   Set_CVarForTest(n"t.MaxFPS", "0");   // prior value captured; restored at finish
//
//   // WRONG — leaks into every later test in this lane:
//   System::ExecuteConsoleCommand("t.MaxFPS 0");
//
//   // ALSO WRONG — "restoring" to a literal imposes YOUR guess of the default
//   // on every later test, which on any project whose default differs is
//   // indistinguishable from not restoring at all:
//   System::ExecuteConsoleCommand("t.MaxFPS 0");
//   ...
//   System::ExecuteConsoleCommand("t.MaxFPS 120");
//
// The base restores every override at finish, on the success AND failure paths,
// so an early FinishFailure cannot skip it. Timing CVars (t.MaxFPS, r.VSync)
// deserve particular care: leaving them moved changes the frame budget of every
// later test in the lane, which surfaces as unrelated wait predicates timing out.
//
// Restoring a CVar means restoring its VALUE **and its SetBy priority**. Writing the old value
// back with a second console command leaves the variable pinned at console priority, so the next
// legitimate lower-priority write (scalability, device profile, project setting) is silently
// ignored for the rest of the process. Set_CVarForTest captures and restores both; that is also
// what makes a properly-scoped override drop back out of the drift report below.
//
// When something OTHER than your test moves a variable on your behalf — HighResShot rewrites
// r.SceneColorFormat / r.PostProcessingColorFormat / r.ForceLOD, and some production paths write
// their own tuning CVars — use Snapshot_CVarForTest(n"name") to capture it without changing it.
//
// Console COMMANDS (viewmode, stat) have no value to capture — if you issue one that changes
// persistent state, put it back yourself, explicitly.
//
// NEVER ASSERT ON INHERITED STATE. An assertion that some global is at its
// default at test start is not testing your feature, it is testing the suite,
// and it fails whenever an unrelated predecessor is imperfect:
//
//   // WRONG — this test fails because some OTHER test left the flag on:
//   if (Subsystem.Get_IsEnabled() != ECk_EnableDisable::Disable)
//   { FinishFailure("the renderer was enabled before anything asked for it"); return; }
//
//   // RIGHT — force the precondition you need, then assert what you own:
//   Subsystem.Request_SetEnabled(ECk_EnableDisable::Disable);
//   Assert_True(Subsystem.Get_IsEnabled() == ECk_EnableDisable::Disable, "starts disabled");
//
// REGISTRIES AND SUBSYSTEM FLAGS have no generic helper — they are per-feature,
// so restore them per-feature. If your test registers a setting, a dialog line, a
// cost provider or a physical button, unregister it (or Track_ForCleanup the
// handle when the registration hands one back). If it flips a subsystem on, flip
// it back. If it writes to disk, it is leaking across RUNS, not just tests — say
// so in review.
//
// THE HARNESS WILL TELL YOU WHEN YOU LEAK A CVAR. ACk_AutoTestRunner fingerprints
// every console variable at a runtime-set priority before your body runs, diffs at
// FinishTest, and logs the delta against YOUR test's name:
//
//   LogCkAutoTest_EnvDrift: Display: [Foo_Actor] left console variables moved
//   after it finished: t.MaxFPS [120] -> [0]. ...
//
// It is advisory (Display, not Warning — a captured Warning would fail the test
// through the opaque log-capture path, see GOTCHA 1). Set
// `ck.AutoTest.StrictEnvironmentDrift 1` to promote drift to a real failure once
// a full-suite run confirms the stream is free of engine-internal churn. Scope:
// ECVF_SetByCode and above only. Everything else on this list is still yours.

// A WALL-CLOCK WAIT IS A SHARED-ENVIRONMENT DEPENDENCY TOO.
//
// A full-suite run spreads tests over N concurrent editors, so a fixed number of
// SECONDS buys markedly fewer FRAMES than the same wait bought when the test ran
// alone — and CkFoundation requests are drained per processor pass, not per second.
// That is why a test can be reliably green solo and red in the suite without any
// other test having leaked a thing.
//
// `ScheduleSettle(2.0f, n"OnX")` — a hand-rolled wall-clock timer copy-pasted into
// 261 test files across ~799 call sites — is the corpus's main exposure here. It is
// not a harness API; each file defines its own. Prefer the base's WaitUntil, which
// converges as soon as the condition holds and names the condition when it never
// does:
//
//   // load-sensitive: 2 seconds is however many frames the machine felt like
//   ScheduleSettle(2.0f, n"OnManned");
//
//   // states what it is waiting for, and is immune to how busy the box is
//   WaitUntil(n"Check_Manned", n"OnManned");
//
// Converting all 799 is a campaign, not a drive-by. Convert the ones you touch, and
// never add a new one.

//============================================================================
// 7. COMMON PATTERNS
//============================================================================

// PATTERN A — Step sequence (the default shape)
// Use when: the test is a linear sequence of do-this, wait-for-that.
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       Add_Step(          "apply the modifier", n"Step_Apply");
//       Add_Step_WaitUntil("bonus reaches +25",  n"Check_BonusApplied");
//       Add_Step(          "revoke it",          n"Step_Revoke");
//       Add_Step_WaitUntil("bonus returns to 0", n"Check_BonusCleared");
//       Run_Steps(InHandle);
//   }
//   UFUNCTION() private void Step_Apply(FCk_Handle InHandle, FInstancedStruct InPayload)
//   { FeatureHandle.Request_X(...); }
//
//   UFUNCTION() private void Check_BonusApplied(
//       FCk_Handle InHandle, FCk_SharedBool OutResult, FInstancedStruct InPayload)
//   {
//       auto Res = OutResult;          // NOT OutResult.Set(...) — see below
//       Res.Set(FeatureHandle.Get_Bonus() == 25);
//   }
//
// The last step finishing passes the test — no trailing FinishSuccess(), and
// no `if (IsFinished())` guard in step bodies. Assertions inside a step are
// tagged with that step's name automatically.
//
// A predicate MUST answer through a local copy. AngelScript treats a by-value
// struct parameter as read-only and rejects `OutResult.Set(...)` with
// "Non-const method call on read-only object reference". FCk_SharedBool holds
// a shared cell, so the copy writes the same bool.

// PATTERN B — Standalone WaitUntil (branching flows)
// Use when: the test branches — net authority splits, or a signal decides
//           which way to go — so a flat step list does not fit.
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       FeatureHandle.Request_X(...);
//       WaitUntil(n"Check_Settled", n"OnSettled");
//   }
//   UFUNCTION() private void OnSettled(FCk_Handle_Timer, FCk_Chrono, FCk_Time) {
//       Assert_Equals_Int(FeatureHandle.Get_<X>(), Expected, "...");
//       FinishSuccess();
//   }
//
// The continuation may start the next WaitUntil, chaining as far as needed.
//
// DO NOT WAIT A FIXED AMOUNT OF TIME OR A FIXED NUMBER OF FRAMES.
// The superseded form of this pattern armed a 0.25s timer and asserted when it
// fired. How many processor passes a deferred effect needs is a property of
// processor ORDERING, not of elapsed time: the constant is a guess that breaks
// when ordering changes, and it silently varies with frame rate in the
// meantime. Worse, when it is wrong the test dies on the engine's TimeLimit
// with an anonymous TimesUp that names nothing. A predicate converges the
// moment it is true and, when it never is, the failure names the pending
// condition. Both forms are self-bounding — they fail ahead of the engine
// timeout — so no hand-rolled _PollCount/budget is needed.

// !!! DO NOT CONVERT A SETTLE THAT GUARDS A NEGATIVE INTO A CONDITION !!!
//
// The migration from a settle to a WaitUntil is only valid when the thing being
// waited for is something that BECOMES true. When the test asserts that
// something does NOT happen — or that a value SURVIVES some event — the naive
// predicate is true the instant it is first evaluated, so the wait returns
// immediately, the event under test never occurs, and the test passes without
// having tested anything. That is strictly worse than the flake it replaced: a
// flaky test is loud, a vacuous one is silent forever.
//
// Real examples in this repo, all left on frame-based settles on purpose:
//   - ObjectPooling_PinnedSurvivesGCThenUnpins — asserts the object SURVIVES a
//     GC. "Object is valid" is true before GC runs, so a condition would return
//     before the GC that is the whole point of the test.
//   - Fog_StartsUnexplored — asserts explored fraction is ~0, true from birth.
//   - EntityTag_RequestTryRemoveAbsentFailed — asserts a no-op did not corrupt
//     the entity. Nothing ever becomes true.
//
// Test for this before converting: "if the system under test did nothing at
// all, would my predicate still be true?" If yes, keep a frame-counted settle
// (WaitFrames / Add_Step_WaitFrames) — it is honest about being a settle.
//
// NOTE: Fog_StartsUnexplored is listed above as an example but has since been
// converted (wave 19) — not by weakening the rule but by finding the POSITIVE
// observable hiding in its own assertion list: Get_CellCounts going non-zero
// proves the grid composed, so the unexplored-everywhere negatives then run
// against a provably live grid. Look for that before settling for frames.
//
// ---------------------------------------------------------------------------

// !!! A PREDICATE ON A SHARED SURFACE MUST NAME *ITS OWN* ENTITIES !!!
//
// Every autotest runs in ONE PIE world. Projection surfaces — compass entries,
// minimap entries, any global registry — therefore contain other tests' data.
// A neighbouring test's entities can still be alive when yours are pending;
// that is exactly why every projection test carries an "Isolated Y band"
// comment in its header.
//
// So this is WRONG, however natural it looks:
//
//     Res.Set(utils_compass::Get_Entries(_Compass).Num() >= 4);   // NO
//
// A count cannot distinguish "my four entries" from "any four entries". It
// releases on a foreign band's POIs and the test asserts against a projection
// that was never its own.
//
// This is not hypothetical — it is how Compass_BearingAtCardinalOffsets failed
// during the wave-21 migration: the compass held exactly 4 entries, none of
// them the test's, and 7 of 9 assertions failed. Six CkMinimap tests shipped
// with the same predicate and PASSED for several gates before the sweep in
// 267bd7e corrected them. Passing is NOT evidence of soundness here.
//
// Name the entities instead:
//
//     auto Entries = utils_compass::Get_Entries(_Compass);
//     auto Found = false;
//     for (auto Entry : Entries)
//     {
//         if (Entry.Get_Poi() == _MyPoi) { Found = true; }
//     }
//     auto Res = OutResult;
//     Res.Set(Found);                                              // YES
//
// If the test has no per-entity handle, key off a category tag private to that
// test (Compass_MaxEntries_PriorityTruncation counts only entries carrying its
// own Poi.Category.TestPriority).
//
// When the test asserts an EXCLUSION, wait on the entity that must SURVIVE.
// That stays a sound structural witness: a broken filter or cull produces EXTRA
// entries, which satisfies the wait and is then reported by the existing
// assertion — there is no state in which the wait hides the defect.
//
// ---------------------------------------------------------------------------

// !!! WAIT ON THE STAGE THE *ASSERTION* DEPENDS ON !!!
//
// A multi-hop settle often spans a CASCADE — several processor passes, each
// producing its own observable. It is easy to collapse those hops into a
// predicate for the FIRST observable stage and leave the assertion checking a
// LATER one. The wait then releases early and the test fails on correct code.
//
// Aggro_OwnerAddThreat_CreatesTarget failed exactly this way during migration.
// Its cascade is create -> Setup -> threat-drain. The predicate gated on the
// tracked target EXISTING; the assertion checks the routed threat value. A
// target is born carrying _InitialThreat (1.0), and the routed 7.0 lands on a
// later pass — so the wait released, the assertion read 1.0, and a > 5.0
// contract failed against a working system. The original code had said so: its
// second hop was commented "create -> Setup -> threat-drain is a multi-pass
// cascade" and existed to span the drain.
//
// Ask: "which stage does my ASSERTION read?" — then wait on that one, not on
// the first thing that becomes observable.
//
// Before waiting on a VALUE rather than an event, confirm it is MONOTONIC in
// the direction you need. Aggro is safe because _ThreatDecayRate defaults to 0,
// so threat cannot rise past the threshold and fall back. Where a value can
// decay, oscillate or be re-clamped, a value predicate can miss its window
// entirely — use the event, or a bounded frame settle, instead.
//
// ---------------------------------------------------------------------------

// !!! CHECK WHETHER THE FILE WAS ALREADY CONVERTED !!!
//
// A test may already carry a WaitUntil from an earlier pass. Adding a second
// wait on the SAME predicate is not a no-op — the predicate is already true, so
// the new wait returns on its first poll and SILENTLY DELETES that settle.
//
// Fog_SetExplored_Roundtrip hit this. Its entry hop already waited for the
// explored fraction to exceed 0.001; a later pass pointed the NEXT hop at the
// same predicate. That happened to also be a duplicate function name, so
// AngelScript refused to compile and the toolbox's AS_COMPILE_FAILED guard
// stopped the run. Without the name collision it would have compiled, gone
// green, and left the test one settle short with no signal anywhere.
//
// Before converting a settle:
//   - `git log --oneline -- <file>` — has a previous pass already touched it?
//   - grep the file for an existing WaitUntil / Check_ predicate.
//   - if a predicate already covers the condition, the extra hop is usually
//     REDUNDANT and should be collapsed, not re-pointed. (In Fog, grid
//     allocation and reveal handling are both upstream of the reveal becoming
//     visible, so one wait spans them and the middle hop simply goes away.)
//
// Any script doing a bulk conversion must assert that the predicate name it
// injects is NEW to that class, alongside its anchor-uniqueness assertions.
//
// ---------------------------------------------------------------------------

// !!! WaitOneFrame IS 0.05s OF WALL-CLOCK, NOT ONE FRAME !!!
//
// Deciding a hop must stay a settle is only HALF the decision. The other half is
// DURATION, and it is an orthogonal axis — a hop can be correctly classified as
// a settle and still be broken by changing how long it settles for.
//
//   WaitOneFrame  = a 0.05s timer  -> ~3 passes at 60fps, ~6 at 120fps, 1 at 20fps
//   WaitFrames(N) = exactly N passes, at any frame rate
//
// WaitFrames is the better instrument when the hop is waiting for a fixed number
// of PROCESSOR PASSES — that is what most deferred-request settles need, and the
// frame count is stable where the timer is not.
//
// But when a window was TUNED against the 0.05s duration, swapping in a small
// frame count SHORTENS it. Transform_ForceRefreshRebroadcasts hit this: its
// pre-bind flush became WaitFrames(2), so the bind + Request_ForceRefresh landed
// while setup was still running, the refresh was absorbed into that pass, and no
// distinct OnUpdate ever broadcast. The test timed out waiting for a rebroadcast
// that legitimately never happened — a working system failed by a shortened
// stimulus.
//
// The same arithmetic is why the CkIskmRenderer socket-follower tests keep their
// hand-rolled `_SettleTicks < 3` loops: three WaitOneFrame fires span ~9 passes
// at 60fps, and WaitFrames(3) would give three.
//
// Rule: converting WaitOneFrame -> WaitFrames(N) is only safe when you can say
// what N is counting. If the hop needs "the pump to drain" (a known small number
// of passes), pick that number. If it is an untuned "let things settle" window
// inherited from wall-clock, LEAVE IT — WaitOneFrame is the correct API there,
// not an unmigrated leftover, and the file should say so in a comment.
//
// ---------------------------------------------------------------------------

// PATTERN C — Signal-driven (PREFER THIS when the feature emits a signal)
// Use when: the framework already broadcasts the transition you are waiting
//           for. Binding it fires exactly on the change with no tick race, so
//           it beats polling — reach for WaitUntil only when no such signal
//           exists, or when the condition is a composite of several
//           observables that no single signal covers.
//
// This is not theoretical. CkAutoTest_Net_Float_Local_AddWorksOnBothWorlds.as
// carries the incident in a comment: "A WaitOneFrame timer (0.05s) can race the
// override-application processor under PIE's faster-than-20fps tick rate and
// read the stale value." Its author replaced the settle with a BindTo_OnValueChanged.
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       auto Local = InHandle;
//       FeatureHandle = utils_*::Add(Local, ...);
//       FeatureHandle.BindTo_OnSomething(FCk_Delegate_*(this, n"OnFired"));
//       FeatureHandle.Request_X(...);
//   }
//   UFUNCTION() void OnFired(...) {
//       if (IsFinished()) return;
//       Assert_*(...);
//       FinishSuccess();
//   }
//
// See: BB_AutoTest_Economy_MoneyFloor.as

//============================================================================
// 8. GOTCHAS & FAILURE MODES
//============================================================================

// GOTCHA 1 — UE_LOG(Warning) during a test = automatic test failure.
//   The automation framework captures all Warning- and Error-level log
//   output and treats it as a test failure regardless of your FinishTest
//   result. Use UE_LOG(Log, ...) for diagnostic prints, or remove them
//   before committing. ck::Trace() with LogLevel::Warning has the same
//   effect — avoid in test code paths.

// GOTCHA 2 — AngelScript boolean negation: use ! NOT NOT.
//   The framework's `NOT` macro is C++-only. AS uses standard `!`:
//     if (!IsFinished()) { ... }   // OK
//     if (NOT IsFinished()) { ... } // Compile error in AS

// GOTCHA 3 — utils_*::Add takes FCk_Handle& (reference), not value.
//   DoBeginPlay receives FCk_Handle by value. Copy to a local first:
//     auto LocalHandle = InHandle;
//     FeatureHandle = utils_*::Add(LocalHandle, Params, ...);

// GOTCHA 4 — Typed handles are typed.
//   utils_integer_attribute::Add returns FCk_Handle_IntegerAttribute.
//   Subsequent calls (BindTo_OnValueChanged, Request_Override, Get_FinalValue)
//   require that typed handle, not generic FCk_Handle. Declare the member
//   as the typed handle.

// GOTCHA 5 — String interpolation of enums.
//   AS f-strings cannot directly format enum values:
//     Print(f"status={MyEnum}");   // Error: invalid type to append
//   Either omit the enum or convert to int/string explicitly.

// GOTCHA 6 — Fragment writes from AS are NOT visible to C++ template Has<T>.
//   AngelScript's FCk_Handle.AddOrGet_Fragment(FType) and C++ template
//   FCk_Handle::Has<T>() use different storage indexing. To bridge data
//   from AS to C++, route through a UFUNCTION on a UBlueprintFunctionLibrary
//   that uses the C++ template path on both sides. The harness already
//   does this for FCk_AutoTest_Result via UCk_Utils_AutoTest_UE.

// GOTCHA 7 — Discovered behavior gaps are real findings.
//   If a test fails because the feature doesn't behave as expected, the
//   test is correct and the feature has a bug. Don't relax assertions to
//   match buggy behavior — the test is the spec.

// GOTCHA 8 — Authority and replication.
//   Set _Replication = ECk_Replication::DoesNotReplicate on test entity
//   scripts (the base class default does this). PIE Standalone runs as
//   listen server, so requests have authority by default.

// GOTCHA 9 — AS `default` syntax requires specific UPROPERTY shapes.
//   AS's `default <Property> = <Value>;` only works when the property
//   has an AS-generated setter binding. Two property shapes get one:
//     a) Engine-module properties (e.g. APawn::bReplicates,
//        AGameModeBase::PlayerControllerClass) — special-cased.
//     b) The CK convention: private/protected field + BlueprintReadOnly +
//        meta=(AllowPrivateAccess=true), e.g. UCk_EntityScript_UE::_Replication.
//   Properties that are PUBLIC + BlueprintReadOnly with NO AllowPrivateAccess
//   on a non-Engine class do NOT get a setter binding, even with NoClear.
//   This is why these all fail:
//     default TimeLimit = 5.0f;                  // public, FunctionalTesting
//     default TestEntityScriptClass = UFoo;      // would fail if public
//   Workarounds (in order of preference):
//     1. For values an AS subclass should provide: declare a
//        UFUNCTION(BlueprintNativeEvent) on the C++ parent and override it
//        via UFUNCTION(BlueprintOverride) in AS. Universal — works for any
//        property regardless of shape. ACk_AutoTestRunner uses this for
//        Get_TestEntityScriptClass.
//     2. For new properties we control on harness classes: follow the CK
//        convention (private `_Field` + AllowPrivateAccess + BPRO). Then
//        `default _Field = Value;` works.
//     3. For class-default values that don't change at runtime: set them
//        in the C++ constructor of the parent. (TimeLimit uses this — set
//        to 5.0 in ACk_AutoTestRunner::ACk_AutoTestRunner.)

// GOTCHA 10 — CkAttribute requests COALESCE within a frame; multi-call
//             tests need a processor tick between requests.
//   `Request_Override`, `Request_Add`, `Request_Sub` etc. on
//   FCk_Handle_IntegerAttribute (and the float/byte equivalents) do NOT
//   enqueue events. They manage a persistent non-revocable modifier on
//   the attribute:
//     - Override: latest call wins (modifier value replaced).
//     - Add/Sub:  delta accumulates into the same modifier.
//     - Mul/Div:  multiplied into the same modifier.
//   When the processor next ticks, it sees the FINAL coalesced state and
//   fires one OnValueChanged + at most one OnMin/MaxClamped signal.
//
//   Wrong shape (only ONE clamp signal fires):
//     Request_Override(Attr, 200);   // would clamp to 100
//     Request_Override(Attr, -50);   // overwrites the 200 before processor sees it
//     // Processor sees only -50, fires OnMinClamped once. OnMaxClamped never fires.
//
//   Right shape (Pattern A, signal-driven):
//     // Step 1: Request_Override(Attr, 200), wait for OnMaxClamped, advance.
//     // Step 2: Request_Override(Attr, -50), wait for OnMinClamped, finish.
//   The wait between steps gives the processor a tick to drain the first
//   request before the second one mutates the same modifier.

// GOTCHA 11 — Leaking entities into the shared PIE world breaks OTHER tests.
//   Every autotest runs in the SAME PIE world, and the harness cascades only
//   the runner's own lifetime subtree. Anything you parent to an ActorRelay
//   channel or to ck::TransientEntity() survives your test — and because
//   features discover their subjects by WORLD-scoped tag-scan, it silently
//   corrupts UNRELATED tests later in the run. The symptom is never local: a
//   test you never touched starts failing an assertion that has nothing to do
//   with your feature. Register every out-of-subtree root with
//   Track_ForCleanup (see §6) — and NEVER register the channel entity itself.

// GOTCHA 12 — There is NO working logging channel inside a headless autotest.
//   Do not waste a run trying to print your way to a diagnosis:
//     - Print(...)        — on-screen debug overlay ONLY. A -nullrhi run has no
//                           screen. Produces nothing in the log.
//     - ck::Warning(...)  — is NOT a log call: it is System::PrintString, which
//                           writes to LogBlueprintUserMessages at `Log` verbosity
//                           (filtered out of the run log) AND warning-level output
//                           during a functional test is escalated to a test
//                           FAILURE. It corrupts the very run you are observing.
//   The ONLY diagnostic channel that reaches the log is the ASSERTION MESSAGE —
//   the C++ runner emits it as `FinishTest TestResult=Failed. Failed: <message>`.
//   So build the diagnostic INTO the assert:
//
//     const bool  SameClock = ...;
//     const int32 Hour      = ...;
//     const FString Diag = f" [DIAG sameClock={SameClock} hour={Hour}]";
//     Assert_True(Condition, "what this asserts" + Diag);
//
//   Precompute every value into a local first — a nested string literal inside
//   an f-string {} block terminates the outer f-string and fails to parse.

// GOTCHA 13 — An Error-level log from ANY subsystem fails whatever test is
//             running, even if that test is innocent.
//   The automation framework escalates Error-level output to a failure on the
//   currently-running test. So an unrelated subsystem erroring mid-run (a source
//   -control fetch failing, a stale external-actor package failing to load, a
//   teardown-order defect) fails a DIFFERENT, random test each run — and looks
//   exactly like flake. Before believing any failure set, grep the run log for
//   `: Error` and check whether the "failing" test even owns the error. Note the
//   category prints WITHOUT the `Log` prefix (e.g. `SourceControl: Error:`).
//
//   This applies to all attribute mutations, not just Override. Reference:
//   CkAutoTest_Attribute_IntegerClamping.as.
//
//   See also: CkAttribute/CLAUDE.md — `Add_NotRevocable` is the coalescing
//   path (single modifier per operation type). `Add_Revocable` creates a
//   distinct modifier entity per call but ALSO doesn't help here, because
//   the modifier processor batches dirty-flagged recomputes per tick.

// GOTCHA 14 — Green alone, red in the suite: read this before "fixing" the
//             test that went red.
//   A lane is ONE editor process running its tests back to back, so a test
//   inherits whatever its predecessors left behind, and the predecessor set
//   CHANGES with the filter: --test-pattern X does not merely run fewer tests,
//   it gives your test different neighbours (or none). Lane width is sized to
//   the machine, so it is not even stable between two full runs on different
//   hardware. "Green in isolation" therefore proves less than it looks like.
//
//   Four different mechanisms produce this shape. Tell them apart BEFORE
//   changing anything, because only the first is the red test's own fault to
//   fix — and the usual mistake is to widen a tolerance in the victim:
//
//   1. STATE LEAKAGE — a predecessor left a console variable, subsystem flag,
//      registry entry or entity behind. Grep the run log for LogCkAutoTest_
//      EnvDrift lines (they name the culprit) and for the leak list in section
//      6. FIX THE CULPRIT, not the victim.
//   2. LOAD / TIMING — N concurrent editors at ~6 GB each shrink the per-test
//      frame budget, so a wait predicate that converges comfortably alone runs
//      out of polls. Tell-tale: "condition never became true within N polls"
//      with a wall time near the budget. Re-run the test alone AND re-run it
//      under a full suite before deciding; do not just raise the budget.
//   3. CAPTURED-LOG NOISE — an Error from any subsystem fails whatever test is
//      running (GOTCHA 13), and which test that is depends on timing. A stale
//      external-actor package is the usual source. Symptom: a failure with zero
//      failed assertions.
//   4. ORDER-DEPENDENT ASSERTIONS — the test asserts on inherited state (see
//      section 6). It is fragile by construction, independent of any leak.
//
//   The A/B that actually settles it: run the red test alone (expect green),
//   then run it with the family that precedes it in the lane (expect red). If
//   the family reproduces it, bisect the family. If it does not, you are looking
//   at 2 or 3, not 1.

//============================================================================
// 9. ONE-TIME PER-PROJECT SETUP
//============================================================================
//
// Each plugin/project that hosts AutoTests sets up three artefacts ONCE:
//   (a) A bare AutoTests level for the AFunctionalTest framework to live in.
//   (b) A UCkAssetRegistryConfig that scans the project/plugin's content
//       and emits typed `assets::<MapName>()` accessors. Most projects
//       already have one for gameplay assets — reuse if present.
//   (c) A UCkAutoTestMapConfig that points at the level via the typed
//       accessor and tells the populator which test classes belong to it.
//       The populator handles per-test placement after that.
//
// Authors creating new tests after this setup do NOT touch any of these
// artefacts — see section 5 (just write the entity script).

//----------------------------------------------------------------------------
// 9a. THE AUTOTESTS LEVEL
//----------------------------------------------------------------------------
//
// One level per plugin/project. Two live in the repo, mirroring the test split:
//
//   Framework-side tests (CkTests plugin — CkAttribute, CkTimer, ...):
//     Plugins/CkTests/Content/AutoTests/AutoTests_CkTests_Level.umap
//
//   Project-side tests (BusterBlock — Economy, Inventory, Store, ...):
//     Content/BusterBlock/Map/AutoTests/AutoTests_BB_MAP.umap
//
// The split mirrors the dependency direction (CkFoundation <- CkTests <-
// BusterBlock) so framework tests are runnable without the project loaded.
//
// Creating the level:
//   1. New empty Level. Save at the path above (or any path your config
//      will point at).
//   2. World Settings -> GameMode Override = AGameModeBase.
//   3. Save.
//
// IMPORTANT: always set GameMode Override = AGameModeBase. If you leave it
// unset, the project's default GameMode (e.g. BbGameMode) runs in the test
// PIE session — initializing player pawn, controllers, gameplay subsystems,
// and any other startup work. That couples every test to project state and
// makes failures depend on project evolution unrelated to the feature under
// test. Tests should be isolated from the game.

//----------------------------------------------------------------------------
// 9b. THE UCkAssetRegistryConfig (typed-accessor scan)
//----------------------------------------------------------------------------
//
// Prerequisite for the recommended UCkAutoTestMapConfig form below. Authors
// the typed `assets::<MapName>()` accessor for your AutoTests level so the
// AutoTestMapConfig can reference it without a magic-string FSoftObjectPath.
//
// Most projects already have one for their gameplay assets — check for an
// existing `asset <Project>Assets of UCkAssetRegistryConfig` declaration
// before authoring a new one. BB's lives at `Script/BB_Assets.as`. CkTests
// has its own at `Plugins/CkTests/Script/CkTests_Assets.as` (covering the
// /CkTests/ plugin content).
//
// Authoring a new config:
//
//   // Plugins/<YourPlugin>/Script/<Plugin>_Assets.as
//   #if editor
//   asset <Plugin>Assets of UCkAssetRegistryConfig
//   {
//       AssetDiscoveryRoot = "/<YourPlugin>/";   // or "/Game/<Subfolder>" for projects
//       OutputFileName = "<Plugin>Assets.as";
//   }
//   #endif
//
// First-time scan: the UCkAssetRegistrySubsystem auto-detects asset
// add/remove/rename inside an existing config's scan root, but does NOT
// auto-scan a brand-new config asset on its first appearance. After
// authoring the .as config, trigger the scan manually via the
// `GenerateAllAssets_CkEditorTools_EUW` editor utility widget in
// CkFoundation/Content/CkEditorOnly/. After the first scan, day-to-day
// asset add/rename/delete inside the scan root regenerates automatically.
//
// Once the scan runs, your level appears in `Plugins/<Plugin>/Script/
// Generated/<Plugin>Assets.as` (or `Script/Generated/<Project>Assets.as`)
// as `assets::<MapName>()` returning `TSoftObjectPtr<UWorld>`.

//----------------------------------------------------------------------------
// 9c. THE UCkAutoTestMapConfig ASSET
//----------------------------------------------------------------------------
//
// Tells the populator which level to keep in sync, scoped to test classes
// authored within the owning plugin. Best authored as an AngelScript
// `asset` declaration — versioned alongside test code, no editor round-trip.
//
//   // Plugins/<YourPlugin>/Script/Common/<Plugin>_AutoTestMapConfig.as
//   #if EDITOR
//   asset <Plugin>_AutoTestMapConfig of UCkAutoTestMapConfig
//   {
//       // Typed accessor from the registry scan in 9b. Refactor-safe:
//       // renaming the .umap regenerates this accessor automatically.
//       TargetMap = assets::<MapName>();
//       // bAutoSaveOnSync defaults to true — no Ctrl+S needed after each
//       // populator pass. Set to false here if you want manual control.
//       // ClassScanRoot is auto-derived from this file's plugin path; only
//       // set it for unusual scopes (multi-plugin, /Game/-only, etc.).
//   }
//   #endif
//
// The #if EDITOR gate is required: UCkAutoTestMapConfig lives in
// CkTestsEditor (UncookedOnly), and AS refuses to bind editor-only types
// in runtime code.
//
// The populator auto-derives the owner-scope filter from where the asset
// is authored:
//   - AS-defined plugin assets — uses the source .as filename (read from
//     ScriptAssetFilename metadata on the asset's package), then matches
//     against IPluginManager to find the plugin → scope = "/<PluginName>/".
//   - AS-defined project assets — when the source .as filename lives under
//     FPaths::ProjectDir() (i.e. it's NOT in a plugin), derives the scope as
//     "<ProjectName>/Script/" (e.g. "BusterBlock/Script/"). The /Script/
//     anchor matters: a bare "/<ProjectName>/" scope would over-match into
//     "<ProjectName>/Plugins/<X>/Script/..." paths and bleed nested-plugin
//     tests into the project's level. Project-side C++ tests under Source/
//     are NOT auto-scoped by this; if you need that, set ClassScanRoot
//     explicitly on the project-side config.
//   - On-disk .uasset configs — uses the package mount point.
// In all cases, with no string fields set the result wraps the owning
// plugin or project naturally, scoping the populator to test classes
// authored inside that owner's source tree.
//
// Fallback if the registry-scan setup isn't viable: TargetMap accepts a
// hand-typed `FSoftObjectPath("/<Path>/<Map>.<Map>")` directly. Works, but
// loses refactor-safety — renaming the .umap silently breaks the config.
//
// Reference configs (drop-in templates):
//   Plugins/CkTests/Script/Common/CkTests_AutoTestMapConfig.as — plugin case
//   <BB>/Script/Tests/BB_AutoTestMapConfig.as — project case
//
// Alternative: a plain UCkAutoTestMapConfig .uasset created via the Content
// Browser still works (Miscellaneous → Data Asset → CkAutoTestMapConfig),
// but offers no benefit over the AS form and adds a binary file to the repo.

//----------------------------------------------------------------------------
// 9d. WHAT THE POPULATOR DOES PER TEST
//----------------------------------------------------------------------------
//
// On every AS post-compile (and on AssetRegistry first-load, and on
// Ck.SyncAutoTestMaps), the populator walks every UCkAutoTestMapConfig
// in the asset registry. Per config:
//   - Resolve the owning plugin from the config's source location.
//   - Discover all live ACk_AutoTestRunner subclasses whose source
//     path is under that plugin (filtered via the auto-derived scope or
//     an explicit ClassScanRoot override).
//   - Pick the world to operate on:
//       * Path A — if the config's TargetMap is the currently-open editor
//         world, sync against that live world. Edits become visible
//         immediately; saves go through the same flow as user edits.
//       * Path B — otherwise, LoadPackage the target .umap off-disk,
//         locate its UWorld, and operate on the unloaded copy. The user's
//         current map is untouched.
//     Either path runs the same downstream logic.
//   - Compare against the wrapper actors currently placed in the chosen
//     world. Spawn missing wrappers; remove orphans (wrapper classes whose
//     entity script was deleted); set Outliner labels by stripping the
//     `_Actor` suffix so Session Frontend rows read cleanly.
//   - On a non-empty delta, MarkPackageDirty + auto-save.
//   - Path A safety guard: if the package was already dirty when the sync
//     started, leave it dirty for manual save. Unrelated user edits in
//     flight must not be silently committed.
//   - Path B "load-induced dirty" handling: if LoadPackage itself dirtied
//     the package (e.g. UE dropped an actor entry whose class no longer
//     exists), the populator saves to persist the cleanup, even if no
//     spawn/remove delta was detected.
//
// Each placed actor becomes one row under
//   Project.Functional Tests.<MapPath>.<ActorLabel>
// in Session Frontend.

//============================================================================
// 10b. READING RESULTS
//============================================================================
//
// After a run completes, four surfaces show what happened. From most useful
// to least:
//
// 1. Session Frontend → click the failed test row → details panel below
//    shows the assertion failure messages from your Assert_*() calls. THIS
//    IS THE PRIMARY DEBUGGING SURFACE — the message you wrote in
//    Assert_Equals_Int(actual, expected, "<message>") shows up here verbatim
//    plus "(expected X, got Y)" appended.
//    If the panel isn't visible, drag the bottom edge of the test tree
//    upward — it's a collapsible split.
//
// 2. Automation Test Graphical Results bar — bottom of Session Frontend's
//    Automation tab, shows a green/red strip per test. Best for "did
//    everything pass?" at a glance.
//
// 3. Output Log filtered to LogAutomationController — structured per-test
//    output: Test Started / Test Completed / failure messages with
//    file:line. Cleaner than the unfiltered log; closer to what CI parses.
//
// 4. Message Log → Automation Testing tab — parallel view of the same
//    data, useful as a fallback if Session Frontend's panel is collapsed
//    or scrubbed.
//
// For headless / CI runs, point -ReportExportPath at a directory and read
// the generated index.html / JSON.

//============================================================================
// 11. SCALING — WHEN TO RESTRUCTURE
//============================================================================

// At ~5 tests:    one map is fine, all tests in it.
// At ~10 tests:   consider splitting maps by feature
//                 (AutoTests_Economy_MAP, AutoTests_Inventory_MAP, ...).
// At ~20+ tests:  per-feature maps are mandatory; running the full suite
//                 in one map gets slow due to PIE startup amortization.
//
// You never need a BP subclass for a test. Anything you might reach for
// BPs to do — variant configs, parameterized reuse, alternate timeouts —
// is expressible as an AS subclass with `default` overrides:
//
//   // Same test body, longer timeout. Hand-authored = generator opts out;
//   // populator picks the hand-authored class up by name. Place it next to
//   // the entity script (NOT under Script/Generated/).
//   class A..._SlowActor : ACk_AutoTestRunner
//   {
//       default _TestEntityScriptClass = U..._BaseTest;
//       default _TimeoutSeconds = 30.0f;
//   }
//
//   // Parameterized entity script (variant pattern):
//   class U..._BaseTest : UCk_AutoTest_Base
//   {
//       UPROPERTY(EditAnywhere, BlueprintReadOnly, meta = (AllowPrivateAccess = "true"))
//       private int32 _ParamA = 10;
//       // ... use _ParamA in DoBeginPlay ...
//   }
//   class U..._VariantTest : U..._BaseTest
//   {
//       default _ParamA = 99;   // override one value, inherit the rest
//   }
//
// CK-shaped UPROPERTYs propagate inheritance naturally — that's the only
// configuration mechanism this harness needs. When you author variant
// entity-script subclasses (U..._VariantTest above), the generator emits a
// fresh A..._VariantTest_Actor wrapper for each, and the populator places
// each wrapper as a separate Session Frontend row. Zero manual upkeep.

//============================================================================
// 14. PURE-C++ UNIT TESTS (the OTHER variation)
//============================================================================

// For features that DO NOT need a ticking world (string formatting, math
// helpers, algorithm utilities, fragment data shape, serialization
// round-trips), skip the AS harness entirely and write a plain C++
// FAutomationTestBase test. Faster to run, no PIE, no actor placement.
//
// DECISION RULE (re-stated):
//   Does the test need processors to tick / signals to fire / a world?
//     Yes -> AS harness (sections 1-13)
//     No  -> C++ unit test (this section)

//----------------------------------------------------------------------------
// FOLDER LAYOUT
//----------------------------------------------------------------------------
//
// Framework-side (CkFoundation utilities):
//   Plugins/CkTests/Source/CkTests/Private/UnitTests/<Module>/Test_<Subject>_<Scenario>.cpp
//
// Project-side (BusterBlock utilities):
//   Source/BusterBlock/Tests/UnitTests/<Module>/Test_<Subject>_<Scenario>.cpp
//
// Mirror the AS path conventions: <Module> groups by feature area, file
// name follows Test_<Subject>_<Scenario> so a directory listing reads as
// a coverage map.

//----------------------------------------------------------------------------
// FILE TEMPLATE
//----------------------------------------------------------------------------
//
//  #include "Misc/AutomationTest.h"
//  #include "<header for subject under test>"
//
//  namespace
//  {
//      // Standard flags for editor-context unit tests. Local constant so
//      // each test file can copy-and-tweak without touching others.
//      constexpr auto kCkUnitTestFlags =
//          EAutomationTestFlags::EditorContext |
//          EAutomationTestFlags::ClientContext |
//          EAutomationTestFlags::ProductFilter;
//  }
//
//  IMPLEMENT_SIMPLE_AUTOMATION_TEST(
//      FCkTest_<Subject>_<Scenario>,
//      "CkTests.UnitTests.<Module>.<Subject>.<Scenario>",
//      kCkUnitTestFlags)
//
//  bool FCkTest_<Subject>_<Scenario>::RunTest(const FString& Parameters)
//  {
//      // ... arrange / act / assert via TestEqual / TestTrue / TestFalse / TestNull / TestNotNull ...
//      return true;   // return false ONLY if the test infrastructure itself failed,
//                     // not for assertion failures (those are tracked by Test*).
//  }
//
// Multiple IMPLEMENT_SIMPLE_AUTOMATION_TEST blocks per file are fine — group
// related scenarios on the same subject. SPUDTest.cpp does this; so does
// Plugins/CkTests/Source/CkTests/Private/UnitTests/Math/Test_CkValueRange_IntRange.cpp.

//----------------------------------------------------------------------------
// NAMING
//----------------------------------------------------------------------------
//
// Class:    FCkTest_<Subject>_<Scenario>      (CkTests-side)
//           FBbTest_<Subject>_<Scenario>      (BusterBlock-side)
// Pretty:   "CkTests.UnitTests.<Module>.<Subject>.<Scenario>"
//           "BusterBlock.UnitTests.<Module>.<Subject>.<Scenario>"
// File:     Test_<Subject>_<Scenario>.cpp
//
// The pretty name is what shows up in Session Frontend. Group all CkTests
// unit tests under "CkTests.UnitTests.*" so they sort together and can be
// filtered as a set.

//----------------------------------------------------------------------------
// ASSERTION API CHEATSHEET (FAutomationTestBase methods)
//----------------------------------------------------------------------------
//
//   TestEqual(What, Actual, Expected)               — compares with ==
//   TestNotEqual(What, Actual, Expected)
//   TestTrue(What, Condition)
//   TestFalse(What, Condition)
//   TestNull(What, Pointer)
//   TestNotNull(What, Pointer)
//   AddError(Message)                                — manual failure
//   AddWarning(Message)                              — non-failing notice
//
// All return bool indicating whether the assertion passed; you can chain
// or guard further work on a previous result if needed.

//----------------------------------------------------------------------------
// WHAT NOT TO DO IN A C++ UNIT TEST
//----------------------------------------------------------------------------
//
//   - Don't touch FCk_Handle, the ECS registry, or any UCk_Utils_*_UE
//     function that requires a world. If you find yourself reaching for
//     these, stop — write an AS test instead.
//   - Don't spawn AActors. They need a world.
//   - Don't tick anything. Tests run synchronously inside RunTest.
//   - Don't UE_LOG(Warning, ...) — automation framework treats warnings
//     as failures (same gotcha as the AS harness, gotcha 1).

//----------------------------------------------------------------------------
// WHEN A "PURE" TEST WANTS A WORLD-LIKE THING
//----------------------------------------------------------------------------
//
// Some utilities take a UWorld* but don't actually require it to tick
// (e.g. asset loaders, UWorld-as-context-handle). Don't try to spin up
// a transient world in a unit test — promote the test to an AS test
// (PIE provides the world for free) instead. The friction of setting up
// a world manually outweighs the convenience of a unit test.
