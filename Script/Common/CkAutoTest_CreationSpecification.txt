// Language=plaintext

//============================================================================
// CK AUTOMATION TEST FRAMEWORK — CREATION SPECIFICATION
//============================================================================

/*
This spec describes the AUTOMATION TEST framework provided by CkTests. It is
project-agnostic: BusterBlock, future projects, and CkTests' own framework
tests all use the same harness.

For the gym framework (visual, manually-driven, no assertions), see:
  CkGym_CreationSpecification.txt

Gyms and AutoTests serve different purposes:
  - Gyms = visual playgrounds for eyeballing a feature.
  - AutoTests = headless assertions that pass/fail in Session Frontend / CI.

A single feature can have BOTH (the gym demonstrates the feature; the
AutoTest verifies it). They share the same .as files where convenient
(both call utils_*::Add, BindTo_*, etc.) but they're independent — the
AutoTest does not need the gym, and vice versa.
*/

//============================================================================
// !!! READ THIS FIRST — THE WORKFLOW IS NOW FULLY AUTOMATED !!!
//============================================================================
//
// Authoring an autotest is a ONE-PART workflow. Write the entity-script .as
// file. Save. Done. The editor pipeline takes care of the rest:
//
//   1. CkAutoTestWrapperGenerator (CkFoundation) — emits the matching
//      A<...>_Actor wrapper class into <Plugin>/Script/Generated/
//      <Plugin>_AutoTestActors.as on every AS post-compile.
//
//   2. UCkAutoTestMapPopulator (CkTestsEditor) — per-config sync that
//      spawns the wrapper actor into the right AutoTests level, sets a
//      readable Outliner label, and auto-saves the level. Triggered by
//      AS post-compile, AssetRegistry first-load, or the
//      `Ck.SyncAutoTestMaps` console command.
//
// IF YOU (HUMAN OR LLM) JUST CREATED OR MODIFIED A TEST:
//   1. Save the .as file. AS auto-recompiles; the wrapper appears in
//      Script/Generated/<Plugin>_AutoTestActors.as.
//   2. The populator runs (you'll see `[CkAutoTest Populator] === ...`
//      in Output Log) and places the wrapper actor into the configured
//      AutoTests level. The level does NOT need to be open — the populator
//      will load the .umap off-disk, edit it, and save it back transparently.
//   3. Run via Session Frontend → Automation tab → check the test →
//      Start Tests. (Or console: `Automation RunTests <pattern>`.)
//
// IF YOU SEE A TEST IN THE .AS FILE BUT NOT IN SESSION FRONTEND:
//   - Refresh Session Frontend (it caches its discovered test list).
//   - Check Output Log for the populator's last summary line — did it find
//     the test? If so, the wrapper actor was spawned in the AutoTests map.
//   - Is there a UCkAutoTestMapConfig for the plugin/project authoring
//     the test? See section 9b for setup.
//   - Did AS report a compile error? A broken .as file blocks PostCompile
//     and stops the generator from running. Fix the AS error first.
//
// The full per-step authoring workflow is in section 5 (file template),
// 5b (per-project config asset), and 9 (one-time map setup).
//
// HISTORICAL NOTE: earlier versions of this framework required authors to
// hand-write the `A<...>_Actor` wrapper class next to the entity script and
// drag it into the AutoTests map manually from the Place Actors panel. Both
// steps are now automated. Hand-authored wrappers still work as an opt-out
// (the generator detects them by class name and skips emission for that
// test) — useful if you need a non-default `_TimeoutSeconds` or a fully
// custom subclass.

//============================================================================
// !!! KNOWN CAVEAT — FILESYSTEM DELETES CAN STRAND THE GENERATED FILE !!!
//============================================================================
//
// AS-UE's file watcher catches modifications reliably but can miss outright
// deletes when they bypass the editor (e.g. `rm`, `git rm`, agent-driven
// filesystem operations). When that happens:
//
//   1. The generator's next PostCompile pass still sees the deleted class
//      as live in AS's class table.
//   2. It emits a wrapper class referencing that now-stale entity script.
//   3. AS's NEXT recompile (triggered by the generator writing the file)
//      fails because the wrapper's `default _TestEntityScriptClass = ...`
//      line references a class AS no longer knows about.
//   4. PostCompile no longer fires (AS compile is broken), so the generator
//      can't fix the file it just emitted. Deadlock.
//
// Recovery (manual):
//   a. Open Script/Generated/<Plugin>_AutoTestActors.as in any editor.
//   b. Delete the broken `class A<DeletedTest>_Actor : ACk_AutoTestRunner
//      { default _TestEntityScriptClass = U<DeletedTest>; }` block.
//   c. Save. AS recompiles cleanly; PostCompile resumes; populator runs.
//   d. The AutoTests map may still have the orphan actor reference on disk;
//      open the level and Ctrl+S once to drop it (or wait for the populator's
//      next path-B sync to detect the load-induced dirty state and save).
//
// PREVENTION:
//   Use the editor's Content Browser to delete .as assets (right-click →
//   Delete). UE-AS's file watcher fires properly through that path and the
//   class is cleanly purged before the generator's next pass. Filesystem
//   deletes are an edge case for power users / scripts; the editor flow
//   is the supported workflow.

//============================================================================
// 1. ARCHITECTURE OVERVIEW
//============================================================================

// Three layers — runtime harness, editor automation, per-test code.
//
//   Layer A — Reusable runtime harness (lives in CkTests):
//     C++:
//       FCk_AutoTest_Result            — USTRUCT result fragment
//       ECk_AutoTest_Status            — Pending/Running/Passed/Failed/TimedOut
//       UCk_Utils_AutoTest_UE          — Set_Result / Has_Result / Get_Result
//       ACk_AutoTestRunner             — AFunctionalTest subclass that drives
//                                        the AS test, applies _TimeoutSeconds
//                                        to the engine TimeLimit, and reports
//                                        pass/fail
//     AngelScript:
//       UCk_AutoTest_Base              — base entity script: Assert_*,
//                                        FinishSuccess/Failure
//
//   Layer B — Editor automation (CkAngelscriptGenerator + CkTestsEditor):
//       FCkAutoTestWrapperGenerator    — on every AS post-compile, scans
//                                        live UCk_AutoTest_Base subclasses
//                                        and emits matching A<...>_Actor
//                                        wrapper classes into <Plugin>/Script/
//                                        Generated/<Plugin>_AutoTestActors.as.
//                                        Skips emission for any test whose
//                                        wrapper class already exists with a
//                                        non-Generated/ source path (the
//                                        opt-out mechanism for hand-authored
//                                        wrappers).
//       UCkAutoTestMapConfig           — UDataAsset (typically authored as
//                                        an AS `asset` declaration) carrying
//                                        target map + auto-save toggle +
//                                        optional scope override.
//       UCkAutoTestMapPopulator        — UEditorSubsystem that, per config,
//                                        ensures one placed wrapper actor
//                                        per discovered test class in the
//                                        config's target level. Triggers on
//                                        AssetRegistry first-load, AS post-
//                                        compile, or `Ck.SyncAutoTestMaps`.
//
//   Layer C — Per-test code (lives in the project):
//     One AS file per test, declaring ONE class — the entity script
//     (subclass of UCk_AutoTest_Base). The corresponding actor wrapper
//     is auto-generated and auto-placed by Layer B. Authors only need
//     to hand-write a wrapper for advanced cases (custom _TimeoutSeconds,
//     fully custom subclass). See section 5b for opt-out details.
//
// Lifecycle (single test run):
//
//   PIE starts on the test map
//       -> AFunctionalTest framework picks up the placed *_Actor
//       -> Runner.PrepareTest syncs TimeLimit to _TimeoutSeconds, then
//          spawns the AS entity on the transient entity via Request_SpawnEntity
//       -> AS DoConstruct runs (base writes Status=Running result fragment)
//       -> AS DoBeginPlay runs (subclass: exercise feature, bind signals)
//       -> Test eventually calls FinishSuccess / FinishFailure
//          -> base class writes Status=Passed/Failed result fragment
//       -> Runner.Tick polls Has_Result; on terminal status, calls
//          FinishTest(Succeeded/Failed, message)
//       -> Session Frontend shows green/red row + assertion message
//
//   If the AS test never writes a terminal result, the engine TimeLimit
//   fires automatically (TimesUpResult=Failed) — no extra harness logic.

//============================================================================
// 2. WHEN TO USE THIS HARNESS (vs C++ FAutomationTestBase)
//============================================================================

// USE THIS HARNESS when the feature under test:
//   - Has processors that mutate state (CkAttribute, CkTimer, Economy, etc.)
//   - Uses Request_*, BindTo_*, signal/messaging infrastructure
//   - Spawns entities, attaches fragments, listens for delegates
//   - Anything that requires a ticking world to behave correctly
//
// In practice, this is ~95% of CkFoundation features and ~all of project
// gameplay code. Decision rule:
//
//   Does the test need processors to tick / signals to fire / a world to exist?
//   |--- Yes -> AS test via this harness.
//   |--- No  -> Plain C++ FAutomationTestBase (no harness needed).
//
// USE PURE C++ TESTS (FAutomationTestBase / IMPLEMENT_SIMPLE_AUTOMATION_TEST)
// only for genuinely-non-world utilities:
//   - ck::Format string utilities
//   - ck::algo::* algorithm helpers
//   - FCk_Chrono / FCk_ValueRange math
//   - SPUD save shape / serialization round-trips
//   - Compile-time / template constraint checks
//   - Any code path that does NOT touch FCk_Handle, processors, or signals
//
// See section 14 for the C++ unit-test layout, naming, and reference example.
//
// NEVER write tests in Blueprint. BPs work via the same UFUNCTION dispatch
// AS uses, but BPs are binary assets — terrible for diffs, code review,
// version control. AS-authored tests are the standard.

//============================================================================
// 3. DEPENDENCY DIRECTION (where tests live)
//============================================================================

// CkFoundation <- CkTests <- ProjectModule (e.g. BusterBlock)
//
// Tests follow the same direction:
//
//   CkFoundation feature tests (CkAttribute, CkTimer, etc.):
//     -> Plugins/CkTests/Script/<ModuleName>/CkAutoTest_<Module>_<Scenario>.as
//
//   Project-specific feature tests (Economy, Inventory, etc. for BusterBlock):
//     -> ProjectRepo/Script/Tests/<Feature>/<Prefix>_AutoTest_<Feature>_<Scenario>.as
//
// The harness in CkTests must NOT depend on project-specific types. The
// per-test AS files own all feature-specific knowledge. The C++ harness only
// references the AS class via TSubclassOf<UCk_EntityScript_UE> and the
// generic FCk_AutoTest_Result struct.

//============================================================================
// 4. NAMING CONVENTIONS
//============================================================================

// Entity-script class:    U<Prefix>_AutoTest_<Feature>_<Scenario>
//   Examples:
//     UCk_AutoTest_Attribute_IntegerBasic        (CkTests, Ck prefix)
//     UBb_AutoTest_Economy_BasicFlow             (BusterBlock, Bb prefix)
//   Authored in the per-test .as file.
//
// Actor wrapper class:    A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor
//   Examples:
//     ACk_AutoTest_Attribute_IntegerBasic_Actor
//     ABb_AutoTest_Economy_BasicFlow_Actor
//   Auto-generated by FCkAutoTestWrapperGenerator into
//     <Plugin>/Script/Generated/<Plugin>_AutoTestActors.as
//   The naming convention IS load-bearing — the generator computes the
//   wrapper name as `A` + entity-script-name-with-`U`-stripped + `_Actor`,
//   and the populator strips the `_Actor` suffix to derive the Outliner
//   label shown in Session Frontend. Don't deviate.
//
// File name:              <Prefix>_AutoTest_<Feature>_<Scenario>.as
//   Holds the entity-script class (and only that, in the typical case).
//
// Folder layout:
//   CkTests:    Plugins/CkTests/Script/<Module>/CkAutoTest_*.as
//   Project:    Script/Tests/<Feature>/<Prefix>_AutoTest_*.as
//
// Test scenario name (the <Scenario> portion):
//   Should describe what the test verifies, not what it does. Good:
//     BasicFlow, MoneyFloor, XPOverflow, IntegerBasic, ClampMaxValue.
//   Bad:
//     Test1, Sanity, Demo, ScratchPad.

//============================================================================
// 5. FILE TEMPLATE
//============================================================================

// Every test file follows this shape — ONE class. The actor wrapper is
// auto-generated by Layer B (see section 1) into Script/Generated/
// <Plugin>_AutoTestActors.as on the next AS recompile. Don't write it
// by hand unless you need an opt-out (section 5b).

class U<Prefix>_AutoTest_<Feature>_<Scenario> : UCk_AutoTest_Base
{
    // ---- Per-test state (handles, step counters, observation fields) ----

    private FCk_Handle_<Feature> FeatureHandle;
    private int32 _Step = 0;

    // ---- Lifecycle: subclasses override DoBeginPlay only ----
    //
    // The base class (UCk_AutoTest_Base) handles DoConstruct: it adds the
    // timeout timer and initializes the Result fragment to Status=Running.
    // Do NOT override DoConstruct unless you have a specific reason to.

    UFUNCTION(BlueprintOverride)
    void DoBeginPlay(FCk_Handle InHandle)
    {
        // 1. Set up the feature being tested.
        //    NOTE: most utils_*::Add calls take FCk_Handle& (ref). DoBeginPlay
        //    receives FCk_Handle by value; copy to a local lvalue first.
        auto LocalHandle = InHandle;
        auto Params = FCk_Fragment_<Feature>_ParamsData(...);
        FeatureHandle = utils_<feature>::Add(LocalHandle, Params, ECk_Replication::DoesNotReplicate);

        // 2. Bind signals. Use these to drive test progression.
        FeatureHandle.BindTo_OnSomething(
            FCk_Delegate_<Feature>_OnSomething(this, n"OnSomethingHandler"));

        // 3. Kick off the first step.
        Step1_DoSomething();
    }

    // ---- Steps: usually one private void Step<N>_<What>() per phase ----

    private void Step1_DoSomething()
    {
        _Step = 1;
        FeatureHandle.Request_DoSomething(...);
    }

    // ---- Signal handlers: assert, then advance to next step or finish ----

    UFUNCTION()
    private void OnSomethingHandler(... payload args ...)
    {
        if (IsFinished()) { return; }

        if (_Step == 1)
        {
            Assert_Equals_Int(observed, expected, "What this assertion verifies");
            FinishSuccess();   // or Step2_DoNext();
        }
    }
}

// That's it. After saving the .as file, the generator emits this:
//
//   // Script/Generated/<Plugin>_AutoTestActors.as  -- DO NOT EDIT
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       default _TestEntityScriptClass = U<Prefix>_AutoTest_<Feature>_<Scenario>;
//   }
//
// And the populator places one instance of that wrapper into the configured
// AutoTests level. Session Frontend picks it up next refresh.

//----------------------------------------------------------------------------
// 5a. ESCAPE HATCH: dynamic test-class resolution
//----------------------------------------------------------------------------
//
// If a wrapper needs to compute its test class at runtime (e.g. based on a
// console var), hand-author the wrapper and override Get_TestEntityScriptClass:
//
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       UFUNCTION(BlueprintOverride)
//       TSubclassOf<UCk_EntityScript_UE> Get_TestEntityScriptClass() const
//       { return SomeCondition ? UClassA : UClassB; }
//   }
//
// The generator detects the hand-authored wrapper by class name and skips
// emission for that test, so the runtime override is authoritative.

//----------------------------------------------------------------------------
// 5b. OPT-OUT: hand-authored wrappers (custom timeout, etc.)
//----------------------------------------------------------------------------
//
// The generator emits wrappers with the engine-default 5s _TimeoutSeconds.
// To use a different timeout — or any other wrapper customization — hand-
// author the wrapper next to the entity-script class:
//
//   class A<Prefix>_AutoTest_<Feature>_<Scenario>_Actor : ACk_AutoTestRunner
//   {
//       default _TestEntityScriptClass = U<Prefix>_AutoTest_<Feature>_<Scenario>;
//       default _TimeoutSeconds = 2.0f;   // fail-fast race-condition test
//   }
//
// The generator recognises any class with the conventional `A<...>_Actor`
// name living OUTSIDE Script/Generated/ as hand-authored and skips emission
// for that test. Reference: CkAutoTest_StateMachine_RacingEventDrivenTransitions.as
// (uses _TimeoutSeconds = 2.0f to surface regressions quickly).

//============================================================================
// 6. THE BASE CLASS API (UCk_AutoTest_Base)
//============================================================================

// Construction (handled by base, do not override unless you need to):
//   - DoConstruct: adds a TAG_CkAutoTest_Runner tag, initializes the
//     Result fragment to Status=Running.
//
// Timeout: configured on the actor wrapper, not on the entity script:
//   class A..._Actor : ACk_AutoTestRunner
//   {
//       default _TimeoutSeconds = 3.0f;   // optional; default is 5s
//   }
// The C++ runner syncs the engine's TimeLimit to _TimeoutSeconds in
// PrepareTest, so there is exactly one knob to configure per test.

// Assertion helpers (call from signal handlers or step functions):
//
//   void Assert_True(bool Condition, const FString& Message);
//   void Assert_Equals_Int(int32 Actual, int32 Expected, const FString& Message);
//   void Assert_Equals_String(const FString& Actual, const FString& Expected,
//                             const FString& Message);
//
// Each assertion increments AssertionsRun. On failure, it increments
// AssertionsFailed and stashes the message as the first failure reason.
// Assertions do NOT auto-finish the test — the subclass decides when.

// Finish helpers (call exactly one of these to end the test):
//
//   void FinishSuccess();                          // No-op if already finished
//   void FinishFailure(const FString& Message);    // No-op if already finished
//   bool IsFinished() const;                       // Use as guard at the
//                                                  // top of signal handlers

// Timeout (automatic):
//   If FinishSuccess/Failure is never called within _TimeoutSeconds (set
//   on the actor wrapper, default 5s), the engine's AFunctionalTest
//   TimeLimit fires and the test is reported as failed. There is no
//   AS-side timer — the engine handles this directly.

//============================================================================
// 7. COMMON PATTERNS
//============================================================================

// PATTERN A — Signal-driven step machine
// Use when: the feature emits a signal per state transition and you want
//           to advance exactly one step per signal.
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       ...bind signal, start step 1...
//   }
//   void Step1() { _Step = 1; FeatureHandle.Request_X(); }
//   void Step2() { _Step = 2; FeatureHandle.Request_Y(); }
//   UFUNCTION() void OnSignal(...) {
//       if (IsFinished()) return;
//       if (_Step == 1) { Assert_*(...); Step2(); }
//       else if (_Step == 2) { Assert_*(...); FinishSuccess(); }
//   }
//
// See: BB_AutoTest_Economy_BasicFlow.as

// PATTERN B — Settle-timer poll
// Use when: a single request triggers complex async behavior (cascading
//           level-ups, multi-frame replication, etc.) and you want to
//           assert on the final state regardless of signal timing.
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       auto Local = InHandle;
//       FeatureHandle = utils_*::Add(Local, ...);
//       // Issue the request immediately.
//       FeatureHandle.Request_X(...);
//       // Schedule a 0.25s settle, then poll.
//       auto Params = FCk_Fragment_Timer_ParamsData(FCk_Time(0.25f));
//       Params.Set_StartingState(ECk_Timer_State::Running)
//             .Set_Behavior(ECk_Timer_Behavior::StopOnDone);
//       auto T = utils_timer::Add(Local, Params);
//       T.BindTo_OnDone(FCk_Delegate_Timer(this, n"OnSettled"));
//   }
//   UFUNCTION() void OnSettled(FCk_Handle_Timer, FCk_Chrono, FCk_Time) {
//       Assert_Equals_Int(FeatureHandle.Get_<X>(), Expected, "...");
//       FinishSuccess();
//   }
//
// See: BB_AutoTest_Economy_XPOverflow.as

// PATTERN C — Single-shot assertion
// Use when: the feature has a one-line behavior to verify (clamp, bounds,
//           conversion, etc.).
//
//   void DoBeginPlay(FCk_Handle InHandle) {
//       auto Local = InHandle;
//       FeatureHandle = utils_*::Add(Local, ...);
//       FeatureHandle.BindTo_OnSomething(FCk_Delegate_*(this, n"OnFired"));
//       FeatureHandle.Request_X(...);
//   }
//   UFUNCTION() void OnFired(...) {
//       if (IsFinished()) return;
//       Assert_*(...);
//       FinishSuccess();
//   }
//
// See: BB_AutoTest_Economy_MoneyFloor.as

//============================================================================
// 8. GOTCHAS & FAILURE MODES
//============================================================================

// GOTCHA 1 — UE_LOG(Warning) during a test = automatic test failure.
//   The automation framework captures all Warning- and Error-level log
//   output and treats it as a test failure regardless of your FinishTest
//   result. Use UE_LOG(Log, ...) for diagnostic prints, or remove them
//   before committing. ck::Trace() with LogLevel::Warning has the same
//   effect — avoid in test code paths.

// GOTCHA 2 — AngelScript boolean negation: use ! NOT NOT.
//   The framework's `NOT` macro is C++-only. AS uses standard `!`:
//     if (!IsFinished()) { ... }   // OK
//     if (NOT IsFinished()) { ... } // Compile error in AS

// GOTCHA 3 — utils_*::Add takes FCk_Handle& (reference), not value.
//   DoBeginPlay receives FCk_Handle by value. Copy to a local first:
//     auto LocalHandle = InHandle;
//     FeatureHandle = utils_*::Add(LocalHandle, Params, ...);

// GOTCHA 4 — Typed handles are typed.
//   utils_integer_attribute::Add returns FCk_Handle_IntegerAttribute.
//   Subsequent calls (BindTo_OnValueChanged, Request_Override, Get_FinalValue)
//   require that typed handle, not generic FCk_Handle. Declare the member
//   as the typed handle.

// GOTCHA 5 — String interpolation of enums.
//   AS f-strings cannot directly format enum values:
//     Print(f"status={MyEnum}");   // Error: invalid type to append
//   Either omit the enum or convert to int/string explicitly.

// GOTCHA 6 — Fragment writes from AS are NOT visible to C++ template Has<T>.
//   AngelScript's FCk_Handle.AddOrGet_Fragment(FType) and C++ template
//   FCk_Handle::Has<T>() use different storage indexing. To bridge data
//   from AS to C++, route through a UFUNCTION on a UBlueprintFunctionLibrary
//   that uses the C++ template path on both sides. The harness already
//   does this for FCk_AutoTest_Result via UCk_Utils_AutoTest_UE.

// GOTCHA 7 — Discovered behavior gaps are real findings.
//   If a test fails because the feature doesn't behave as expected, the
//   test is correct and the feature has a bug. Don't relax assertions to
//   match buggy behavior — the test is the spec.

// GOTCHA 8 — Authority and replication.
//   Set _Replication = ECk_Replication::DoesNotReplicate on test entity
//   scripts (the base class default does this). PIE Standalone runs as
//   listen server, so requests have authority by default.

// GOTCHA 9 — AS `default` syntax requires specific UPROPERTY shapes.
//   AS's `default <Property> = <Value>;` only works when the property
//   has an AS-generated setter binding. Two property shapes get one:
//     a) Engine-module properties (e.g. APawn::bReplicates,
//        AGameModeBase::PlayerControllerClass) — special-cased.
//     b) The CK convention: private/protected field + BlueprintReadOnly +
//        meta=(AllowPrivateAccess=true), e.g. UCk_EntityScript_UE::_Replication.
//   Properties that are PUBLIC + BlueprintReadOnly with NO AllowPrivateAccess
//   on a non-Engine class do NOT get a setter binding, even with NoClear.
//   This is why these all fail:
//     default TimeLimit = 5.0f;                  // public, FunctionalTesting
//     default TestEntityScriptClass = UFoo;      // would fail if public
//   Workarounds (in order of preference):
//     1. For values an AS subclass should provide: declare a
//        UFUNCTION(BlueprintNativeEvent) on the C++ parent and override it
//        via UFUNCTION(BlueprintOverride) in AS. Universal — works for any
//        property regardless of shape. ACk_AutoTestRunner uses this for
//        Get_TestEntityScriptClass.
//     2. For new properties we control on harness classes: follow the CK
//        convention (private `_Field` + AllowPrivateAccess + BPRO). Then
//        `default _Field = Value;` works.
//     3. For class-default values that don't change at runtime: set them
//        in the C++ constructor of the parent. (TimeLimit uses this — set
//        to 5.0 in ACk_AutoTestRunner::ACk_AutoTestRunner.)

// GOTCHA 10 — CkAttribute requests COALESCE within a frame; multi-call
//             tests need a processor tick between requests.
//   `Request_Override`, `Request_Add`, `Request_Sub` etc. on
//   FCk_Handle_IntegerAttribute (and the float/byte equivalents) do NOT
//   enqueue events. They manage a persistent non-revocable modifier on
//   the attribute:
//     - Override: latest call wins (modifier value replaced).
//     - Add/Sub:  delta accumulates into the same modifier.
//     - Mul/Div:  multiplied into the same modifier.
//   When the processor next ticks, it sees the FINAL coalesced state and
//   fires one OnValueChanged + at most one OnMin/MaxClamped signal.
//
//   Wrong shape (only ONE clamp signal fires):
//     Request_Override(Attr, 200);   // would clamp to 100
//     Request_Override(Attr, -50);   // overwrites the 200 before processor sees it
//     // Processor sees only -50, fires OnMinClamped once. OnMaxClamped never fires.
//
//   Right shape (Pattern A, signal-driven):
//     // Step 1: Request_Override(Attr, 200), wait for OnMaxClamped, advance.
//     // Step 2: Request_Override(Attr, -50), wait for OnMinClamped, finish.
//   The wait between steps gives the processor a tick to drain the first
//   request before the second one mutates the same modifier.
//
//   This applies to all attribute mutations, not just Override. Reference:
//   CkAutoTest_Attribute_IntegerClamping.as.
//
//   See also: CkAttribute/CLAUDE.md — `Add_NotRevocable` is the coalescing
//   path (single modifier per operation type). `Add_Revocable` creates a
//   distinct modifier entity per call but ALSO doesn't help here, because
//   the modifier processor batches dirty-flagged recomputes per tick.

//============================================================================
// 9. ONE-TIME PER-PROJECT SETUP
//============================================================================
//
// Each plugin/project that hosts AutoTests sets up two artefacts ONCE:
//   (a) A bare AutoTests level for the AFunctionalTest framework to live in.
//   (b) A UCkAutoTestMapConfig asset telling the populator which level
//       to keep in sync. The populator handles per-test placement after that.
//
// Authors creating new tests after this setup do NOT touch either artefact —
// see section 5 (just write the entity script).

//----------------------------------------------------------------------------
// 9a. THE AUTOTESTS LEVEL
//----------------------------------------------------------------------------
//
// One level per plugin/project. Two live in the repo, mirroring the test split:
//
//   Framework-side tests (CkTests plugin — CkAttribute, CkTimer, ...):
//     Plugins/CkTests/Content/AutoTests/AutoTests_CkTests_Level.umap
//
//   Project-side tests (BusterBlock — Economy, Inventory, Store, ...):
//     Content/BusterBlock/Map/AutoTests/AutoTests_BB_MAP.umap
//
// The split mirrors the dependency direction (CkFoundation <- CkTests <-
// BusterBlock) so framework tests are runnable without the project loaded.
//
// Creating the level:
//   1. New empty Level. Save at the path above (or any path your config
//      will point at).
//   2. World Settings -> GameMode Override = AGameModeBase.
//   3. Save.
//
// IMPORTANT: always set GameMode Override = AGameModeBase. If you leave it
// unset, the project's default GameMode (e.g. BbGameMode) runs in the test
// PIE session — initializing player pawn, controllers, gameplay subsystems,
// and any other startup work. That couples every test to project state and
// makes failures depend on project evolution unrelated to the feature under
// test. Tests should be isolated from the game.

//----------------------------------------------------------------------------
// 9b. THE UCkAutoTestMapConfig ASSET
//----------------------------------------------------------------------------
//
// Tells the populator which level to keep in sync, scoped to test classes
// authored within the owning plugin. Best authored as an AngelScript
// `asset` declaration — versioned alongside test code, no editor round-trip.
//
//   // Plugins/<YourPlugin>/Script/Common/<Plugin>_AutoTestMapConfig.as
//   #if EDITOR
//   asset <Plugin>_AutoTestMapConfig of UCkAutoTestMapConfig
//   {
//       TargetMap = FSoftObjectPath(
//           "/<YourPlugin>/AutoTests/<YourMap>.<YourMap>");
//       // bAutoSaveOnSync defaults to true — no Ctrl+S needed after each
//       // populator pass. Set to false here if you want manual control.
//       // ClassScanRoot is auto-derived from this file's plugin path; only
//       // set it for unusual scopes (multi-plugin, /Game/-only, etc.).
//   }
//   #endif
//
// The #if EDITOR gate is required: UCkAutoTestMapConfig lives in
// CkTestsEditor (UncookedOnly), and AS refuses to bind editor-only types
// in runtime code.
//
// The populator auto-derives the owner-scope filter from where the asset
// is authored:
//   - AS-defined assets — uses the source .as filename (read from
//     ScriptAssetFilename metadata on the asset's package), then matches
//     against IPluginManager to find the plugin → scope = "/<PluginName>/".
//   - On-disk .uasset configs — uses the package mount point.
// In both cases, the result is "/<YourPlugin>/" with no string fields set.
//
// Reference: Plugins/CkTests/Script/Common/CkTests_AutoTestMapConfig.as
// (the framework's own validation rig — drop-in template for downstream
// projects).
//
// Alternative: a plain UCkAutoTestMapConfig .uasset created via the Content
// Browser still works (Miscellaneous → Data Asset → CkAutoTestMapConfig),
// but offers no benefit over the AS form and adds a binary file to the repo.

//----------------------------------------------------------------------------
// 9c. WHAT THE POPULATOR DOES PER TEST
//----------------------------------------------------------------------------
//
// On every AS post-compile (and on AssetRegistry first-load, and on
// Ck.SyncAutoTestMaps), the populator walks every UCkAutoTestMapConfig
// in the asset registry. Per config:
//   - Resolve the owning plugin from the config's source location.
//   - Discover all live ACk_AutoTestRunner subclasses whose source
//     path is under that plugin (filtered via the auto-derived scope or
//     an explicit ClassScanRoot override).
//   - Pick the world to operate on:
//       * Path A — if the config's TargetMap is the currently-open editor
//         world, sync against that live world. Edits become visible
//         immediately; saves go through the same flow as user edits.
//       * Path B — otherwise, LoadPackage the target .umap off-disk,
//         locate its UWorld, and operate on the unloaded copy. The user's
//         current map is untouched.
//     Either path runs the same downstream logic.
//   - Compare against the wrapper actors currently placed in the chosen
//     world. Spawn missing wrappers; remove orphans (wrapper classes whose
//     entity script was deleted); set Outliner labels by stripping the
//     `_Actor` suffix so Session Frontend rows read cleanly.
//   - On a non-empty delta, MarkPackageDirty + auto-save.
//   - Path A safety guard: if the package was already dirty when the sync
//     started, leave it dirty for manual save. Unrelated user edits in
//     flight must not be silently committed.
//   - Path B "load-induced dirty" handling: if LoadPackage itself dirtied
//     the package (e.g. UE dropped an actor entry whose class no longer
//     exists), the populator saves to persist the cleanup, even if no
//     spawn/remove delta was detected.
//
// Each placed actor becomes one row under
//   Project.Functional Tests.<MapPath>.<ActorLabel>
// in Session Frontend.

//============================================================================
// 10b. READING RESULTS
//============================================================================
//
// After a run completes, four surfaces show what happened. From most useful
// to least:
//
// 1. Session Frontend → click the failed test row → details panel below
//    shows the assertion failure messages from your Assert_*() calls. THIS
//    IS THE PRIMARY DEBUGGING SURFACE — the message you wrote in
//    Assert_Equals_Int(actual, expected, "<message>") shows up here verbatim
//    plus "(expected X, got Y)" appended.
//    If the panel isn't visible, drag the bottom edge of the test tree
//    upward — it's a collapsible split.
//
// 2. Automation Test Graphical Results bar — bottom of Session Frontend's
//    Automation tab, shows a green/red strip per test. Best for "did
//    everything pass?" at a glance.
//
// 3. Output Log filtered to LogAutomationController — structured per-test
//    output: Test Started / Test Completed / failure messages with
//    file:line. Cleaner than the unfiltered log; closer to what CI parses.
//
// 4. Message Log → Automation Testing tab — parallel view of the same
//    data, useful as a fallback if Session Frontend's panel is collapsed
//    or scrubbed.
//
// For headless / CI runs, point -ReportExportPath at a directory and read
// the generated index.html / JSON.

//============================================================================
// 11. SCALING — WHEN TO RESTRUCTURE
//============================================================================

// At ~5 tests:    one map is fine, all tests in it.
// At ~10 tests:   consider splitting maps by feature
//                 (AutoTests_Economy_MAP, AutoTests_Inventory_MAP, ...).
// At ~20+ tests:  per-feature maps are mandatory; running the full suite
//                 in one map gets slow due to PIE startup amortization.
//
// You never need a BP subclass for a test. Anything you might reach for
// BPs to do — variant configs, parameterized reuse, alternate timeouts —
// is expressible as an AS subclass with `default` overrides:
//
//   // Same test body, longer timeout. Hand-authored = generator opts out;
//   // populator picks the hand-authored class up by name. Place it next to
//   // the entity script (NOT under Script/Generated/).
//   class A..._SlowActor : ACk_AutoTestRunner
//   {
//       default _TestEntityScriptClass = U..._BaseTest;
//       default _TimeoutSeconds = 30.0f;
//   }
//
//   // Parameterized entity script (variant pattern):
//   class U..._BaseTest : UCk_AutoTest_Base
//   {
//       UPROPERTY(EditAnywhere, BlueprintReadOnly, meta = (AllowPrivateAccess = "true"))
//       private int32 _ParamA = 10;
//       // ... use _ParamA in DoBeginPlay ...
//   }
//   class U..._VariantTest : U..._BaseTest
//   {
//       default _ParamA = 99;   // override one value, inherit the rest
//   }
//
// CK-shaped UPROPERTYs propagate inheritance naturally — that's the only
// configuration mechanism this harness needs. When you author variant
// entity-script subclasses (U..._VariantTest above), the generator emits a
// fresh A..._VariantTest_Actor wrapper for each, and the populator places
// each wrapper as a separate Session Frontend row. Zero manual upkeep.

//============================================================================
// 14. PURE-C++ UNIT TESTS (the OTHER variation)
//============================================================================

// For features that DO NOT need a ticking world (string formatting, math
// helpers, algorithm utilities, fragment data shape, serialization
// round-trips), skip the AS harness entirely and write a plain C++
// FAutomationTestBase test. Faster to run, no PIE, no actor placement.
//
// DECISION RULE (re-stated):
//   Does the test need processors to tick / signals to fire / a world?
//     Yes -> AS harness (sections 1-13)
//     No  -> C++ unit test (this section)

//----------------------------------------------------------------------------
// FOLDER LAYOUT
//----------------------------------------------------------------------------
//
// Framework-side (CkFoundation utilities):
//   Plugins/CkTests/Source/CkTests/Private/UnitTests/<Module>/Test_<Subject>_<Scenario>.cpp
//
// Project-side (BusterBlock utilities):
//   Source/BusterBlock/Tests/UnitTests/<Module>/Test_<Subject>_<Scenario>.cpp
//
// Mirror the AS path conventions: <Module> groups by feature area, file
// name follows Test_<Subject>_<Scenario> so a directory listing reads as
// a coverage map.

//----------------------------------------------------------------------------
// FILE TEMPLATE
//----------------------------------------------------------------------------
//
//  #include "Misc/AutomationTest.h"
//  #include "<header for subject under test>"
//
//  namespace
//  {
//      // Standard flags for editor-context unit tests. Local constant so
//      // each test file can copy-and-tweak without touching others.
//      constexpr auto kCkUnitTestFlags =
//          EAutomationTestFlags::EditorContext |
//          EAutomationTestFlags::ClientContext |
//          EAutomationTestFlags::ProductFilter;
//  }
//
//  IMPLEMENT_SIMPLE_AUTOMATION_TEST(
//      FCkTest_<Subject>_<Scenario>,
//      "CkTests.UnitTests.<Module>.<Subject>.<Scenario>",
//      kCkUnitTestFlags)
//
//  bool FCkTest_<Subject>_<Scenario>::RunTest(const FString& Parameters)
//  {
//      // ... arrange / act / assert via TestEqual / TestTrue / TestFalse / TestNull / TestNotNull ...
//      return true;   // return false ONLY if the test infrastructure itself failed,
//                     // not for assertion failures (those are tracked by Test*).
//  }
//
// Multiple IMPLEMENT_SIMPLE_AUTOMATION_TEST blocks per file are fine — group
// related scenarios on the same subject. SPUDTest.cpp does this; so does
// Plugins/CkTests/Source/CkTests/Private/UnitTests/Math/Test_CkValueRange_IntRange.cpp.

//----------------------------------------------------------------------------
// NAMING
//----------------------------------------------------------------------------
//
// Class:    FCkTest_<Subject>_<Scenario>      (CkTests-side)
//           FBbTest_<Subject>_<Scenario>      (BusterBlock-side)
// Pretty:   "CkTests.UnitTests.<Module>.<Subject>.<Scenario>"
//           "BusterBlock.UnitTests.<Module>.<Subject>.<Scenario>"
// File:     Test_<Subject>_<Scenario>.cpp
//
// The pretty name is what shows up in Session Frontend. Group all CkTests
// unit tests under "CkTests.UnitTests.*" so they sort together and can be
// filtered as a set.

//----------------------------------------------------------------------------
// ASSERTION API CHEATSHEET (FAutomationTestBase methods)
//----------------------------------------------------------------------------
//
//   TestEqual(What, Actual, Expected)               — compares with ==
//   TestNotEqual(What, Actual, Expected)
//   TestTrue(What, Condition)
//   TestFalse(What, Condition)
//   TestNull(What, Pointer)
//   TestNotNull(What, Pointer)
//   AddError(Message)                                — manual failure
//   AddWarning(Message)                              — non-failing notice
//
// All return bool indicating whether the assertion passed; you can chain
// or guard further work on a previous result if needed.

//----------------------------------------------------------------------------
// WHAT NOT TO DO IN A C++ UNIT TEST
//----------------------------------------------------------------------------
//
//   - Don't touch FCk_Handle, the ECS registry, or any UCk_Utils_*_UE
//     function that requires a world. If you find yourself reaching for
//     these, stop — write an AS test instead.
//   - Don't spawn AActors. They need a world.
//   - Don't tick anything. Tests run synchronously inside RunTest.
//   - Don't UE_LOG(Warning, ...) — automation framework treats warnings
//     as failures (same gotcha as the AS harness, gotcha 1).

//----------------------------------------------------------------------------
// WHEN A "PURE" TEST WANTS A WORLD-LIKE THING
//----------------------------------------------------------------------------
//
// Some utilities take a UWorld* but don't actually require it to tick
// (e.g. asset loaders, UWorld-as-context-handle). Don't try to spin up
// a transient world in a unit test — promote the test to an AS test
// (PIE provides the world for free) instead. The friction of setting up
// a world manually outweighs the convenience of a unit test.
